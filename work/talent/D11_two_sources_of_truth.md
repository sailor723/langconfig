# 决定项 D11：岗位要求的权威在哪一边 —— 公理，还是 `requirement` 表？

> 这是目前唯一一个拦在 apply 之前、且**不能由我决定**的架构问题。
> 下面每个数字都是在本机实测出来的，不是估计。

---

## 1. 问题是什么

岗位要求现在同时存在于两个地方，而**两者各自都能独立判定"谁合格"**：

| | 公理（`reasoning.ttl`） | `requirement` 表 |
|---|---|---|
| 形态 | `:matches_<岗位> ≡ :Candidate ⊓ ∃hasSkill.:skillsFor_<岗位> ⊓ ∃yearsExperience[≥N] ⊓ ∃educationRank[≥M]`<br>其中 `:skillsFor_X ≡ :Cat1 ⊔ :Cat2 ⊔ …`（类别 OR） | 31 行（26 essential + 5 desirable），每行带 `kind` / `tier` / `threshold` / `verbatim` / 零件列表 |
| 判定方式 | HermiT 蕴含 | 覆盖率 ≥ 0.5 + 年限/学历作评分 |
| 决定什么 | **成员资格** | **评分与闸门** |
| 出处 | 无 | 每行带 JD 原话与文件名 |
| 能否表达"读不到 ≠ 不合格" | ❌ | ✅（unknowns / completeness） |
| 能否表达复合要求与阈值 | ❌ | ✅ |
| 能否被门禁重算 | ✅（`check_abox_sync` 逐行） | ✅（`fit_component` 逐行） |

## 2. 实测：两个裁判只在 13% 上一致

同一个 `talent_db`、同一批 277 份简历：

| 岗位 | 仅技能 OR（必要条件） | 现行公理 | 评分闸门 | **公理 ∩ 闸门** |
|---|---|---|---|---|
| 专案工程师 | 78 | 25 | 14 | **1** |
| 业务助理 | 54 | 20 | 55 | **5** |
| 业务跟单 | 175 | 48 | 37 | **10** |
| 人资专员 | 138 | 0 | 8 | **0** |
| 关务报关员 | 32 | 0 | 7 | **0** |
| 副总助理 | 137 | 35 | 55 | **12** |
| 品质经理 | 114 | 25 | 0 | **0** |
| 工程文员 | 198 | 0 | 55 | **0** |
| 招聘专员 | 97 | 31 | 13 | **4** |
| 管理课长 | 97 | 20 | 55 | **6** |
| **合计（跨岗）** | **1120** | **204** | **299** | **38** |

**公理给 204，闸门给 299，交集只有 38 —— 一致率 13%。**

差异的来源是可列举的，不是噪声：
- **年限/学历**：公理把它们当硬门槛（挡掉 129 无年限 + 71 无学历），闸门按 D10 把它们移出成员判定 → 公理里 166 人不被闸门接受
- **技能语义**：公理是"类别 OR"（很松），闸门是"每条复合要求覆盖率 ≥ 0.5"（多零件要求更严）→ 闸门里 261 人不被公理接受
- **人资专员/工程文员**：公理 0 人而闸门 8/55 人 —— 因为这两个岗位的 JD **没有声明年限门槛**，而公理里仍然带年限 facet，等于替客户发明了一条门槛

## 3. 三个选项

### 选项 A — 公理唯一权威（`requirement` 表降级为"证据与措辞"）
- 名单 = HermiT 的蕴含结果；`requirement` 表只用来渲染理由、存 JD 原话
- ✅ 单一计算路径，`check_abox_sync` 已经是现成的门禁
- ❌ 表达不了复合覆盖率、阈值、tier、以及**"读不到 ≠ 不合格"**
- ❌ 每次改词表/阈值都是改 TBox + 重推理；那 10 条不可评估要求永远无法诚实表达
- ❌ 等于把 `requirement` 表整个废弃——本轮做的工作作废

### 选项 B — `requirement` 表唯一权威（公理只保留类结构）
- 名单 = 覆盖率闸门；`:matches_*` 定义停止参与判定
- ✅ 复合/阈值/tier/unknown 都能表达；改动是数据编辑不是本体编辑
- ❌ 推理机不再是裁判，`check_abox` / `check_abox_sync` 对名单变成摆设
- ❌ 本体的意义被掏空——"这份 CV 到底算不算这个岗位"退化成一个 SQL 条件

### 选项 C — 分层：公理判"能不能"，`requirement` 判"够不够"（**推荐**）

| 问题 | 归公理 | 归 requirement 表 |
|---|---|---|
| 是不是这个岗位的候选人（**必要条件**） | ✅ `∃hasSkill.(该岗位要求的类别)` —— 开放世界里"至少会一项相关技能"正是 OR 能表达的 | |
| 复合要求满足几成、门槛 0.5 | | ✅ 覆盖率 |
| 哪条必须、哪条优先 | | ✅ tier（有 JD「优先」字样才降级） |
| 年限 / 学历 | | ✅ 评分项（D10：退出成员判定） |
| "读不到" vs "不合格" | | ✅ unknowns / completeness |
| 技能家族近似（D9） | ✅ 类层级给 family | ✅ 给具体分值 |

判定顺序：**公理是入口（必要条件）→ requirement 闸门是闸 → 两者皆过才算 qualified。分歧必须显式报出，不许一方默默盖掉另一方。**

**改造成本很小**：公理只需要**删掉 `∃yearsExperience` 与 `∃educationRank` 两个 facet**，`∃hasSkill.(类别 OR)` 保留原样——因为它本来就是一条必要条件，不是门槛。

实测这条路的后果：

| 岗位 | C：必要条件 ∩ 闸门 | 现行：公理 ∩ 闸门 | 变化 |
|---|---|---|---|
| 专案工程师 | 14 | 1 | +13 |
| 业务助理 | 13 | 5 | +8 |
| 业务跟单 | 26 | 10 | +16 |
| 人资专员 | 8 | 0 | +8 |
| 关务报关员 | 7 | 0 | +7 |
| 副总助理 | 55 | 12 | +43 |
| 品质经理 | 0 | 0 | 0 |
| 工程文员 | 55 | 0 | +55 |
| 招聘专员 | 13 | 4 | +9 |
| 管理课长 | 22 | 6 | +16 |
| **合计** | **213** | **38** | **+175** |

品质经理仍然是 0（**语料里没有品质专才**，与模型无关——见 `stage_extended_vocab.md` §4）。

## 4. 我推荐 C，并给出三条理由

1. **每一层做它擅长的事**：描述逻辑擅长表达开放世界的**必要条件**（"必须至少会一项相关技能"），不擅长表达"满足六成"；关系代数擅长后者。硬让一方干另一方的活，就是现在这 13% 一致率的来源。
2. **它保住了门禁**：`check_abox_sync` 继续有意义（公理层可被逐行重算），`fit_component` 也可被逐行重算。选项 B 会让两个门禁对名单失效。
3. **它把"不可评估"变成一等公民**：10 条抽不出来的要求，在 C 里如实标为 `assessable=false` 并在名单上显示"差哪一项"，而不是像 A 那样只能判成"不合格"。

## 5. 选 C 之后必须一并确定的三件小事

1. **分歧如何披露**：公理说合格而闸门说不够（或相反）时，名单上要不要单独一栏？我建议要——这正是 D6"被排除的人必须可见"的同一原则。
2. **`reasoning.ttl` 里 4 个"没有 JD"的岗位**（行政专员/技术经理主管/设计工程师/实验室技术员，共 54 人）在公理里本来就不存在 `:matches_*`，C 下保持拒绝，不生成。
3. **`role.required_years` 为 NULL 的岗位**（人资专员、工程文员、关务报关员）在公理 facet 删除后自然处理正确——现在它们被一条客户没声明的年限门槛挡成 0 人，这是 C 顺带修掉的 bug。

## 6. 待你决定

- **选 A / B / C**（我推荐 C）
- 若选 C：是否同意**从公理里删掉 `:yearsExperience` 与 `:educationRank` 两个 facet**（这是 C 的唯一必要改动，且是对 D10 的直接落实）

定了之后，apply 的顺序是：改公理 → `materialize.py`（活库）→ `check_abox_sync` 应绿 → `apply(confirmed=True)`。
