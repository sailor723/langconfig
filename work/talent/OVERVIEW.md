# 招聘流水线 · 总览（演示用）

> 一页讲完：**怎么走完一次招聘**、**每一步业务做什么、技术怎么实现**、**凭什么信结论**。
> 数字由 `scripts/talent/build_overview.py` 从产物现算，不手写（`--check` 可校验是否过期）。

## 一句话

**客户 JD 上传 → 对 40 格标准模板查缺口 → HR 与业务定稿（缺的格先 mock 满）→ 初筛 + HR 一面补齐 CV 并写评语 → 短名单 ≤10 → 选 5 人给业务面，并附每人一份问题清单。**

**交接关系**：业务交原文 → HR+业务交定稿 → HR 交面试名单与一面记录（含评语）→ HR+业务交短名单 → 业务+HR 交最终 5 人 + 业务面问题清单 → 用人部门面这 5 人。
每一步都落成文件；下一步只读上一步的产物，不靠人转述。

> **阶段口径**（2026-11-24 定）：Phase 0 = 标准定义（字段/组件/要求/模板，跟具体 JD 无关）；Phase 1 = 上传一份 JD、抽原文、出缺口；Phase 2 = HR 与业务定稿；之后才是第 3–5 步的选人。

## 第 ① 步 · 出初始 JD

### 业务视角

- **谁**：业务（招聘需求方）。**什么时候**：岗位一开就做。
- **做什么**：把客户给的职务说明书**原样**交上来。不解释、不润色、不改错别字、不合并同类项。
- **判断标准**：客户到底写了什么。业务不做"意思大概是这样"的翻译 —— 那一步是第 ② 步、而且要签字。
- **交付**：一份原始文件 + 一句"这份是哪个岗位"。

### 技术视角

| 项 | 内容 |
|---|---|
| 落盘 | `work/talent/jd_links/_source/<JD>.txt`（.doc/.docx/.xlsx 抽平成文本，每行带行号） |
| 为什么保留原文 | 后面每一条要求都要能**逐字回查**到这里的某一行；原文动了，所有引用立刻作废 |
| 工具 | `extract_jd` / `llm_draft_jd` 起草引用；`jd_links/_source` 是只读锚点 |
| 门禁 | 逐字回查：`verbatim` 必须在原文里且 `txt_line` 真的指向那一行（改一个字就红） |

## 第 ② 步 · 定稿（把原文变成闸门）

### 业务视角

- **谁**：HR + 业务一起。**什么时候**：初筛之前，必须定稿。
- **做什么**：逐条确认"这句是客户的意思吗"；把客户没写清的地方列成待确认；我方要补的要求（例如到岗周期）必须标明**我方提出**并写依据。
- **判断标准**：客户原文优先。客户说"优先"就是优先，不许写成"必须"；客户没说阈值，就记"没法判"，**不许替客户定一个数**。
- **交付**：一张要求清单（每条带客户原话和行号）+ 一份决策账本（谁定了什么、哪天、为什么还没签）。

### 技术视角

| 项 | 内容 |
|---|---|
| 引用文件 | `jd_links/<JD>.yaml`：66 条引用（客户 61 + 我方 HR 侧 5），每条带 `verbatim` / `txt_line` / `origin` / `tier` / 阈值 `value` |
| 要求库 | `requirement_library.yaml`（61 条）：阈值算子、数据项、可判性（`assessable`）、阈值口径 |
| 转正脚本 | `promote_jd`：草稿逐条复核 verbatim 与行号，**任一条对不上就整体拒绝、一个文件都不写** |
| 决策账本 | `jd_reviews/<JD>.yaml`：粒度/阈值/覆盖三类决定，一律 `signoff: pending` 等业务签字 |
| 回填参数 | `jd_inputs/<JD>.yaml`：面试人数、短名单区间、`final_max`、业务优先条件 |
| 门禁 | 引用逐字性、行号真实、HR 侧不许冒充客户原话、带拆分信号的引用必须有粒度决定且账本里有对应条目 |

## 第 ③ 步 · 初筛 + HR 一面（必须）：决定谁值得面，并把 CV 补齐

### 业务视角

- **谁**：HR。**什么时候**：定稿之后、打电话之前。
- **做什么**：从简历池里**只**剔除"简历上明确写着不合格"的人（例如客户写 25~40 岁、简历写 45 岁）。
- **判断标准**：读不到 ≠ 不合格。凡是拿不准的，一律留在池子里，进**待核清单**，等电话里问。
- **交付**：一份面试名单（HR 真能打完电话的数量）+ 一份待核清单（按谁问、怎么问写清楚）+ **补齐的 CV**（每人一份定稿）+ **HR 评语**（这个人怎么样，一句话也要有证据）。

### 技术视角

| 项 | 内容 |
|---|---|
| 初筛 | `screen_cv`：只对"简历直接写着"的属性阈值判；算子不是阈值的、推导出来的量、白名单带"等/类"的**都不拿来排除人** |
| 账要平 | `kept + excluded = pool`，门禁断言；差一个人就说明有人被静默丢掉 |
| 面试名单 | `pick_interview_list`：九层证据阶梯排序 + 切线 `tie_band`（并列几个人写进产物，名次可读不可读由它决定） |
| 待核清单 | `open_questions`：按人 × 按条款生成；每条写清谁问、给什么问法 |
| 一面（必须） | `simulate_hr_round`（演练；真访谈时换成真人记录）：按待核清单把 JD 要的数据问齐，答案 `basis` 标 `interview` / `simulated` |
| CV 补齐 | `render_all_cv` → `cv_docs/<人>.定稿.md`（31 字段逐格标来源）+ `index_cv` → `<JD>.CV清单.md`（含 **HR 评语** 列） |
| HR 评语 | `mock_hr_comment` → `cv_interview/<人>.yaml` 的 `review`：**不进判定**，只给人读；每条都要能追到证据（硬证据几项、一面几条、填充度） |
| 门禁 | **排除必须有硬证据**；待核的人必须还在池里；每条排除都能追到值；CV 定稿每格必须标来源 |

## 第 ④ 步 · 加面（**可选**）

### 业务视角

- **谁**：HR / 业务。**什么时候**：第 ③ 步之后，**需要时**才做 —— 这一步不是必须的。
- **做什么**：对拿不准的人再补一轮（能力举例、加面确认）。**跳过不是缺**：没问的格子记「未知」，不是「不合格」。
- **判断标准**：**不问"你觉得他行不行"**，也不打分。只记录：问了什么、他怎么答、能不能举例。
- **交付**：追加的问答记录（并回 CV 定稿）；没有加面就什么都不用交，流程照样往下走。

### 技术视角

| 项 | 内容 |
|---|---|
| 记录 | `cv_interview/<候选人>.yaml`：`answers[]` 每条带 `basis`（`interview` 真访谈 / `simulated` 代拟）、`establishes`（坐实了哪条要求的能力项） |
| 采信规则 | 规则是**数据**：`interview_policy.yaml` 的 `mode`。默认 `real_only` —— 代拟答案不进判定 |
| 档案 | `render_cv_final` 产出 `cv_docs/<候选人>.定稿.md`：字段全集 + 每格标来源（`resume` / `代拟(模拟)` / `interview`），并写明填充度 |
| 演练模式 | `simulate_hr_round`：按待核清单 + JD 能力项生成答案，**坐实/否认跟着简历证据走**，不按哈希随机 |
| 门禁 | 每条答案 `basis` 必须诚实；`establishes` 必须落回某条要求；能力「满足」必须标证据强度 |

## 第 ⑤a 步 · 短名单（谁排前面）

### 业务视角

- **谁**：HR。**什么时候**：一面做完。
- **做什么**：把面过的人排一个"够格进下一轮评估"的名单，人数按 HR 定的上限（当前 ≤10）。
- **判断标准**：**证据多的排前面**（有载体/能核实的证据优先于只有自述），然后才看业务偏好、客户写的"优先"条款、年限、稳定性。
- **交付**：一份有顺序的名单 + 切线说明（切在第几名、那里是否并列）。

### 技术视角

| 项 | 内容 |
|---|---|
| 脚本 | `shortlist_after_interview` → `shortlist/<JD>.目标名单.yaml` 的 `selected` |
| 证据 | 简历抽到的能力项 ∪ 一面坐实的；按 `component_catalog` 的 `evidence_role` 分硬/软 |
| 排序 | 九层阶梯：硬证据 → 软证据 → 业务优先条件 → 客户「优先」条款 → 年限 → 稳定性 → 待核项 → 品质岗经历 → 哈希兜底 |
| 门槛口径 | `REQ-B-MAJOR`（专业）**不进硬门槛**：客户写的是"…等"开区间，且口径未定（DEF-04） |
| 门禁 | 进名单的人必须面过且在本 JD 面试名单内；人数 ≤ 上限；切线 `tie_band` 必须交代 |

## 第 ⑤b 步 · 最终名单（谁没有硬伤）

### 业务视角

- **谁**：HR + 业务。**什么时候**：短名单之后，送去用人部门面之前。
- **做什么**：从短名单里取出**送去面试的那 5 个人**。
- **判断标准**：三条硬条件 —— 客户硬门槛 **0 条不满足**、至少 **1 项硬证据**、未知 **≤3 条**；上限 5 人。**不够 5 个就如实说不够，不硬凑。**
- **交付**：5 人名单 + 每人一段"为什么是他" + **每人一份业务面问题清单**（A 能力举例 / B 当面确认未知项 / C 岗位必答）。

### 技术视角

| 项 | 内容 |
|---|---|
| 产物 | 同文件的 `final`（含 `unknown_max` / `min_hard` / `max`，门禁照产物复核，不写死数字） |
| 选人 | `pick_final`：**不重排**，直接按名单顺序取；只补逐人理由与判定说明 |
| 判定说明 | `explain_rejection` → `verdicts/<JD>/<人>.md|yaml`：每条判定带客户原文、行号、数据项、他的值、阈值、值来源、四态 |
| 业务面问题 | `business_questions` → `picks/<JD>.业务面问题.md`：每人三段 —— A 能力项（软证据要举例 / 硬证据当面核对载体）、B 当面确认（判定「未知」格 + 客户门槛「不满足」格，逐条带客户原话）、**C 岗位必答**。**不生成"你觉得他行不行"这类问题** |
| 门禁 | 最终名单 ⊂ 短名单、人数 ≤ 上限、**人数明显更少**、每人真的过三条硬条件（从 `rows` 复算，不信自报）、说明不得过期 |

## 排序口径：名单是怎么"切"出来的

> 唯一权威就是本节。代码在 `pick_interview_list`（面试名单）与 `shortlist_after_interview`（短名单/最终名单），两处产物里都写着 `rank_rule` 与 `cut`。
> **本节与代码不一致时，以代码 + 产物为准**，并回来把本节改掉 —— 文档不能变成第二个真相。

**九个层，前面的决定后面的。** 上一层分不出胜负才看下一层；越靠前越硬，哈希永远在最后。

| 层 | 依据 | 数据来源 | 谁能改 |
|---|---|---|---|
| ① | **硬证据项数**（可验证载体：系统/报告/客户审核/图表） | 简历抽取能力项 ∩ JD 要求组件中 `evidence_role: hard`，按**能力**去重 | 系统固定 |
| ② | **软证据项数**（只能靠陈述） | 同上，`evidence_role: soft` | 系统固定 |
| ③ | **业务优先规则命中数** | `priority_catalog.yaml` 里用户挑的那几条 | **用户** |
| ④ | **客户原文「…优先」条款命中数** | JD 中 `verbatim` 含「优先」的条款，判定=满足才计 | 客户原文（自动） |
| ⑤ | **总年限**（多者前） | 平台计算年限 | 系统固定 |
| ⑥ | **稳定性：平均在职年限** | `hr_facts.avg_tenure_years`（从工作段算出） | 系统固定 |
| ⑦ | **待核项数**（少者前） | `open_questions/<JD>.yaml` | 系统固定 |
| ⑧ | **品质岗经历强度**（有 > 待核 > 读不出 > 无） | `cv_quality.verdict` | 系统固定；**本 JD 不要求品质经历时这一层关闭** |
| ⑨ | **`sha256(候选人 id)`** | — | 系统固定；**不按姓名/文件名排** |

### 只能动的三个旋钮

| 旋钮 | 命令 | 影响 |
|---|---|---|
| 人数 | `set_target --jd <JD> --interview N --shortlist M~K` | 切几刀 |
| 业务优先规则 | `priorities --jd <JD> --select 2 5` | 只影响第 ③ 层 |
| 清空规则 | `priorities --jd <JD> --clear` | 第 ③ 层归零，回到纯证据排序 |

**其余七层不能靠对话改。** 要改先改政策，改完同时更新本节、代码里的 `rank_rule`、以及 agent prompt —— 三处必须一致。

### "他的名次能不能读"——看 `cut.tie_band`

```yaml
cut:
  position: 10          # 切在第几位
  tie_band: 1           # 这个位置上有几个人排序键完全相同
  hash_decided: false   # 名次是否由哈希决定
  note: 切线唯一 —— 名次可读
```

| tie_band | 含义 | 汇报怎么说 |
|---|---|---|
| **1** | 切线唯一 | 名次可读，可以说"他排第 N" |
| 2~3 | 小并列 | "这几个人键相同，谁上都行，按哈希排" |
| >3 | 大片并列 | "**切线落在并列区内，名次不可读**；集合有意义，顺序没有" |

**不许**在 `tie_band > 1` 时说"他更合适"—— 那是把哈希说成判断。
当前五条线的 `tie_band` 见上面漏斗表的「切线并列」列。

### 为什么是这个顺序（设计理由，不是偏好）

1. **证据在最前**：能不能干这个活是第一位，偏好不能压过证据。（曾把用户规则放最前，结果"规则全中但零能力证据"的人排到第 5 —— 已改。）
2. **客户的「优先」在第 ④**：排用户规则之后，因为用户规则是本轮招聘的临时取舍，客户原文是长期口径；两者都是"偏好"，不是"资格"。
3. **年限在稳定性之前**：客户写了「N 年以上经验」，这是客户口径；稳定性是我方推断。
4. **待核项数是成本指标**：信息完整的人先面能省钱，但**不代表他更合适**。
5. **哈希兜底而不是 id**：按 id 排等于按文件名/姓氏排，是一种看不见的偏差。

### 已知偏差（必须一起说）

| 层 | 偏差 | 方向 |
|---|---|---|
| ① ② | 用的是**简历抽取词表**，偏向"简历写得细的人"（DEF-01） | 会漏判能力：说不清的人被排后 |
| ④ | 客户只写"专业优先"这类弱条款时，该层常命中 0 人 | 该层失效，不产生偏差也不起作用 |
| ⑤ | 年限**读不出来**的排最后 —— 这是**排序口径，不是判他不合格** | 信息不全的人被排后 |
| ⑥ | 平均在职年限是我方推断量，客户原文没要求 | 可能压掉"跳槽多但能力强"的人 |

### 怎么验证这份口径没走样

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.pick_interview_list --jd <JD>
env -u PGPORT .venv/bin/python -m scripts.talent.shortlist_after_interview --jd <JD>
env -u PGPORT .venv/bin/python -m scripts.talent.check_component_catalog
```

门禁会核：`rank_rule` 必须是 **9 层**、必须有 `cut` 段、`tie_band` 必须是整数、面试名单人数等于 `interview_target`、账必须平（`kept + excluded = pool`）、最终名单必须是短名单真子集且明显更少。**同输入重跑必须逐字节相同** —— 不确定就不算"可复算"。
