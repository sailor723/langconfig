# 排序口径:面试名单是怎么"切"出来的

> 唯一权威。代码在 `backend/scripts/talent/pick_interview_list.py`,产物在
> `work/talent/shortlist/<JD>.面试名单.yaml` 的 `rank_rule` 与 `cut` 两段。
> 本文与代码不一致时,以**代码+产物**为准,并把本文改过来 —— 别让文档变成第二个真相。

## 一、九个层,前面的决定后面的

上一层分不出胜负,才看下一层。**越靠前越硬,哈希永远在最后。**

| 层 | 依据 | 数据来源 | 谁能改 |
|---|---|---|---|
| ① | **硬证据项数**(可验证载体:系统/报告/客户审核/图表) | 简历抽取的技能 ∩ JD 要求组件中 `evidence_role: hard` 的项,按**能力**去重 | 系统固定 |
| ② | **软证据项数**(只能靠陈述:英语自评、"会分析") | 同上,`evidence_role: soft` | 系统固定 |
| ③ | **业务优先规则命中数** | `work/talent/priority_catalog.yaml` 里用户挑的那几条 | **用户** |
| ④ | **客户原文写的「…优先」条款命中数** | JD 里 `verbatim` 含「优先」的条款,按判定=满足计 | 客户原文(自动) |
| ⑤ | **总年限**(多者前) | 平台计算年限 | 系统固定 |
| ⑥ | **稳定性:平均在职年限** | `hr_facts.avg_tenure_years`(从工作段算出) | 系统固定 |
| ⑦ | **待核项数**(少者前) | `open_questions/<JD>.yaml` | 系统固定 |
| ⑧ | **品质岗经历强度**(有>待核>读不出>无) | `cv_quality.verdict` | 系统固定;**JD 不要求品质经历时这一层关闭** |
| ⑨ | **`sha256(候选人 id)`** | — | 系统固定;**不按姓名/文件名排** |

## 二、只能动的三个旋钮

| 旋钮 | 命令 | 影响 |
|---|---|---|
| 目标人数 | `set_target --jd <JD> --interview 30 --shortlist 8~12` | 切几刀 |
| 业务优先规则 | `priorities --jd <JD> --select 2 5` / `--select P-IND-HARNESS` | 只影响第 ③ 层 |
| 清空规则 | `priorities --jd <JD> --clear` | 第 ③ 层归零,回到纯证据排序 |

**其余七层不能靠对话改**。要改先改政策(例如"稳定性该不该用"),改完同时更新本文、
代码里的 `rank_rule`、以及 agent prompt —— 三处必须一致。

## 三、"他的名次能不能读"——看 `cut.tie_band`

产物里有这一段:

```yaml
cut:
  position: 10          # 切在第几位
  tie_band: 1           # 这个位置上有几个人排序键完全相同
  hash_decided: false   # 名次是否由哈希决定
  note: 切线唯一 —— 名次可读
```

| tie_band | 含义 | 汇报怎么说 |
|---|---|---|
| **1** | 切线唯一 | 名次可读,可以说"他排第 N" |
| 2~3 | 小并列 | "这几个人键相同,谁上都行,按哈希排" |
| >3 | 大片并列 | "**切线落在并列区内,名次不可读**;集合有意义,顺序没有" |

**不许**在 `tie_band > 1` 时说"他更合适"——那是把哈希说成判断。

## 四、为什么是这个顺序(设计理由,不是偏好)

1. **证据在最前**:能不能干这个活是第一位;偏好不能压过证据。
   (曾经把用户规则放最前,结果"规则全中但零能力证据"的人排到第 5 —— 已改。)
2. **客户的「优先」排在第 ④**:它排在用户规则之后,因为用户规则是本轮招聘的临时取舍,
   客户原文是长期口径。两者都是"偏好",不是"资格"。
3. **年限在稳定性之前**:客户写了「N 年以上经验」,这是客户口径;稳定性是我方推断。
4. **待核项数是成本指标**:信息完整的人先面能省钱,但这**不代表他更合适**。
5. **哈希兜底而不是 id**:按 id 排等于按文件名/姓氏排,是一种看不见的偏差。

## 五、已知偏差(必须一起说)

| 层 | 偏差 | 方向 |
|---|---|---|
| ① ② | 用的是**简历抽取词表**,偏向"简历写得细的人"(见 DEF-01) | 会漏判能力:说不清的人被排后 |
| ④ | 客户只写了「专业优先」这类弱条款时,该层常命中 0 人(实测业务跟单 0/270) | 该层失效,不产生偏差也不起作用 |
| ⑤ | 年限**读不出来**的排最后 —— 这是**排序口径,不是判他不合格** | 信息不全的人被排后 |
| ⑥ | 平均在职年限是我方推断量,客户原文没要求 | 可能压掉"跳槽多但能力强"的人 |

## 六、怎么验证这份口径没走样

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.pick_interview_list --jd <JD>
env -u PGPORT .venv/bin/python -m scripts.talent.check_component_catalog
```

门禁会核:`rank_rule` 必须是 **9 层**、必须有 `cut` 段、`tie_band` 必须是整数、
名单人数必须等于 `interview_target`、账必须平(`kept + excluded = pool`)。

同输入重跑必须逐字节相同 —— 不确定就不算"可复算"。

## 七、当前实测(2026-11-22)

| JD | 池子 | 目标 | 第①层并列 | 切线 tie_band | 名次可读? |
|---|---|---|---|---|---|
| 品质经理 | kept 164 | 30 | 待重跑(旧阶梯产物) | — | — |
| 业务跟单 | kept 270 | 10 | **50 人同为硬证据 2 项** | **1** | ✅ 可读 |

业务跟单能切线唯一,靠的是 ⑤⑥⑦ 三层(年限 10/5/4/2 年、在职 4.3/3.1/1.6、
待核 1/2/3)。**换句话说:这份名单的名次是"经验+稳定+资料完整度"排出来的,不是"能力"排出来的** ——
因为 50 个人的能力证据完全相同。要真正按能力分,只能进第 4 步面谈。
