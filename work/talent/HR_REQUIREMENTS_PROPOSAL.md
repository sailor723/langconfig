# HR 维度应该写成 JD 里的一类要求 —— 结论与提案

> 写于 2026-11-20 · 起因:第 4b 步「HR 一面出评语」原本打算另建一套 1–5 打分表
> 结论:**不建打分表。HR 的维度就是要求,和客户要求放在同一套机制里。**
> 本文只做三件事:说清为什么、划清一条不能越的线、给出待 HR 签字的提案。

---

## 一、为什么这个结论是对的(不只是"更优雅")

原方案(另一套打分表)有三个躲不掉的问题:

1. **两套判据打架。** join 说"满足 7 条",打分表说"3 分",业务领导不知道该信谁。
   而且没有任何机制能解释这两者为什么不同 —— 因为它们本来就不是一个尺子量出来的。
2. **打分表没有出处。** 客户的每条要求都能回查到原话第几行;而"稳定性给 3 分"回查不到
   任何东西。整个系统最值钱的性质(每一条判定都能回查)在这里断掉。
3. **加权就没了尽头。** 60/25/15 之外再加 HR 权重,等于承认"分数"是个可以无限调的旋钮。
   而实测已经说明:74% 的人同分并列,分数本身分不开人。

改成"HR 维度 = 要求"之后,这三条同时消失:

- **一个机制**:要求 → 数据项 → 四态(满足/不满足/未知/不可判)。HR 要求走同一条路。
- **每一条都有出处**:`author: HR` + `rationale`(为什么提这条),门禁强制要求。
- **不引入新旋钮**:HR 要求要么满足、要么不满足、要么未知。没有"几颗星"。

顺带解决一件实事:**现在有 15 个 CV 字段是"死字段"** —— 简历里有值,但 JD 那边没有
对应要求,所以永远不参与判定(`compare: cv_only`)。HR 加要求之后,其中几个立刻活过来:

| 字段 | CV 出现 | 现在 | 加 HR 要求之后 |
|---|---|---|---|
| 到岗日期 | 123 份 | 死字段 | 可判(到岗 ≤ N 周) |
| 工作地点 | 113 份 | not_comparable | 可判(通勤半径) |
| 薪资 | 71 份 | not_comparable | 可判(在预算区间内) |
| 公司名称 | 255 份 | 死字段 | 喂给"稳定性" |
| 起止时间 | 267 份 | 死字段 | 喂给"平均在职时长" |

## 二、一条不能越的线:客户原话 ≠ HR 要求

这是本文最重要的一节。**把 HR 的要求写进 JD,和替客户改 JD,只隔一层纸。**
之前就犯过一次:把"我方建议"写进了 JD 定稿正文,被指出来"你编了必要的东西"。

所以引用文件里现在有**两类出处**,结构上分开,门禁上强制:

| | 客户原话 `origin: client` | HR 侧要求 `origin: hr` |
|---|---|---|
| 有没有原话 | 有,`verbatim` 必须是客户文件里的逐字子串 | **没有**。不许带 `verbatim`/`txt_line`/`source_text` |
| 必填 | `verbatim` / `source_text` / `txt_line` | `author` / `rationale` |
| 回查方式 | 回查客户原文的行号 | 回查"谁提的、为什么提" |
| 渲染位置 | JD 定稿正文 | **单独一章,不进客户正文** |

门禁已经实现并验证有牙齿(`check_component_catalog.py`):

```
正式文件:  161 checks · 0 failed · green
注入变异:  161 checks · 2 failed · RED
  ① 把一条客户原话改成 origin:hr 但保留 verbatim → FAIL(HR 侧要求不冒充客户原话)
  ② 给一条 HR 要求去掉 author/rationale      → FAIL(没理由的要求不许进 JD)
```

顺带修掉一个真问题:这道引用门禁(122 条逐字回查)**原先默认不跑** —— 不传 `--links`
就静默跳过。"要记得加参数才跑"的门禁和没有这道门是一个效果。现在默认就跑。

## 三、提案:6 条 HR 侧要求(待签字)

下面每一条都写了:**判据 / 数据项 / 现在能不能取到 / 要新建什么**。
「现在能不能取到」是按实测的 CV 出现率说的,不是我猜的。

| # | HR 侧要求 | 判据 | 数据项 | 现在能拿到 | 要新建 |
|---|---|---|---|---|---|
| H1 | 到岗时间不超过 4 周 | `到岗日期 ≤ 4 周` | F.AVAILABILITY | **是**,CV 123/270 + 一面必问 | 属性补 `notice_weeks`(周数,现在是自由文本) |
| H2 | 期望薪资落在岗位预算内 | `薪资 ≤ 预算上限` | F.SALARY | 部分,CV 71/270 + 平台归档 | 已经有了,只缺 JD 侧预算上限这个取值 |
| H3 | 通勤可接受 | `现居地到厂区 ≤ 60 分钟` | F.WORK_LOCATION | **否**,CV 是自由文本("住石排镇") | 需要"到厂区距离/时长"这个可计算量,或改成"是否接受该地点"的是非题 |
| H4 | 稳定性:近 5 年任职公司不超过 3 家 | `近 5 年公司段数 ≤ 3` | **C.4 在岗时长 / 新增 tenure** | **可以算**,工作经历解析已经能切出段数与起止(公司 64% · 职位 52% · 职责 42%) | C.4 的 `prop_exists` 从 false 转 true,并写明段数的算法 |
| H5 | 平均在职时长不低于 2 年 | `逐段累计 ÷ 段数 ≥ 2 年` | C.4 / C.6 | 同上,且可重算 | 与 H4 共用同一个属性 |
| H6 | 一面印象(沟通、态度、动机) | —— | **无** | 不能 | 这条**不该**写成要求(见第四节) |

### 我建议的落法

- **H1 / H2 / H4 / H5** 写成正式要求(`origin: hr`),进 join。它们有明确判据、能出四态。
- **H3** 先改成是非题(「能否接受在石排上班」),因为自由文本的距离算不出来;
  硬要算就要引入地图服务,那是另一个量级的事。
- **H6 不写。** 它没有数据项,写进去只会多一条永远"不可判"的要求,
  反而稀释了"不可判"这个状态的含义。一面的整体印象留在档案里给业务领导看,
  **不参与计算** —— 这跟我上一版建议的"结构化打分"不一样,原因见下。

## 四、我要收回上一版的一个建议

上一版我建议"HR 评语用几个固定维度打 1–5 分,参与 join"。
按你这次的说法想过一遍,这个建议是错的:

**打分表和"要求"是同一个东西的两种写法,而后者能被检验、前者不能。**

- 「沟通表达 4 分」是什么意思?谁定的 4 分算好?换个人打几分为准?
- 「沟通协调能力达到 XX」是一条要求 —— 但它没有数据项,所以它诚实地说"不可判"。

同一条意思,写成要求就自动得到四态里的"不可判",不用另外发明一个刻度。
所以:**能写成要求的,写成要求;写不成要求的(没有数据项),就不进计算。**
HR 的打分冲动,应该被翻译成"HR 到底在担心什么" —— 那个担心通常能落成一条要求。

例:"我觉得他不太稳定" → H4「近 5 年任职公司 ≤ 3 家」(可判);
"我觉得他态度一般" → 落不成要求,那就别假装能算。
