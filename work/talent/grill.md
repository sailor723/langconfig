## 二、待定（3 条 + 第二轮改写后的 3 条硬结论）

第二轮（阈值 + 部分分实验，见 `B_experiment.md`）把 O1/O2 拆细了，并且**否掉了原来的问法**：

| # | 原问题 | 第二轮之后 |
|---|---|---|
| O1 | 家族亲疏的部分分值给多少（0.6? 0.8?） | **问法作废**。分数不用魔法数，用覆盖率 `held/parts`；但**粒度受制于复合项的 parts 数**（见 N2） |
| O2 | 聚合公式：加权平均 / 闸门 / 求和封顶 | **改写成 N3**：区分度缺口不在公式里，靠改公式解决不了 |
| O3 | top-10 人工判定由谁签 | 不变。D7 已定"要判定"，签字人未定，不阻塞实现 |
| **O4** | **未知项在评分里的地位**（第三轮新增） | 见下（已推荐"两条名单"，代码已实现） |
| **D11** | **岗位要求的权威在哪一边**（stage 后新增，**拦在 apply 之前**） | 全文见 `D11_two_sources_of_truth.md` |

### 第二轮的三条硬结论

**N1 — 技能分层（tier）没有文本依据，必须由客户确认。**
26 条从 JD 抽出的要求**全部**落到 `essential`，因为 10 份 JD 里没有任何"这条技能必须／那条优先"的措辞。
JD 里唯一的"优先"信号落在**专业与行业**上，不在技能上（5 条 desirable 全部来自此）。
→ **不许我们替客户发明技能优先级。**

**N2 — 部分分的粒度 = 复合项的 parts 数，不是可调旋钮。**
实验实测：阈值 0.34 与 0.5 结果**完全等价**，0.67 与 1.0 也等价。
因为复合项只有 2–3 个组成部分，覆盖率被量化成 0 / 0.33 / 0.5 / 0.67 / 1.0。
→ **`composite` 的 parts 拆多细，直接决定分数精度**；这比选 0.6 还是 0.8 重要得多。

**N3 — 区分度缺口在三个地方，不在聚合公式。**
闸门 + 覆盖率分数实测仍只有 **2–3 个不同分值**（专案工程师 14 人挤在 83.3/100.0 两档）。
一旦"必须全中"当闸门，合格者的覆盖率天然挤在 [0.5, 1.0] 窄带；年限封顶 1.0、学历二值（`fit.py:32-37`）也没动。
真正能提供区分度的只有：
1. **desirable 层可评估化**（现 5 条，全部不可评估）——唯一的"加分项"来源
2. **年限／学历从二值改梯度**（D10 只定了它们退出闸门，没定怎么计分）
3. **技能深度而非有无**——但 JD 只说"熟练/熟悉/具备"，**没有刻度**，须客户定义

### O4 — 未知项在评分里的地位（第三轮，待定）

第三轮的实测把这条逼出来了（详见 `B_experiment.md` §16–17）：

- 第一版做法「未知项从分母剔除再归一化」**会奖励读不出来**：专案工程师 62 个满分者里，
  **48 个是因为年限/学历没读到而满分**。被追问「为什么他第一」时答案是「因为没读到」——与 D1 冲突。
- 四种排序策略实测（top-10 中信息完整者）：只按分数 **8/10**；分数+完整度 **10/10**；
  完整度优先 10/10 但太强；两条名单结构上不会混。

**我的推荐：(iv) 两条名单** —— 完整信息者一张、部分信息者一张，各自内部按（分数, 年限, id）排。
理由：不发明任何折算公式；与 D2（进名单并标记）、D6（未纳入要可见）同源；
而 (ii) 只修好了"100 对 100 谁在前"，没修"不完整的 100 排在完整的 87.5 之前"。

**这条是口径问题，该用户定。** 代码已实现 `score_v2()` / `order_key_v2()` / `rank_rows_v2()`，
默认不启用，四种排序都能在同一份数据上切换比较。

### 第三轮的实现状态

`backend/scripts/talent/fit.py` 新增（v1 一行未动）：
- `YEARS_BANDS` / `EDU_BANDS` — 分档表，数据驱动（年限倍率实测横跨 0–7×，v1 封顶 1×）
- `score_v2(...)` → `(score, completeness, unknowns)`
- `order_key_v2()` / `rank_rows_v2()` — 分数 → 完整度 → 年限 → id

区分度实测：v1 的 2–24 档 → v2 的 **16–80 档**（每岗位提高 2–4 倍）。

## 三、D4 落地：两张台账（形状已定，字段待审）

## 四、已知的硬限制（不是决定，是事实，别再重新发现一遍）

1. **OCR 原文没有留存**。`candidate_skill` 只有 (candidate, skill)。所以 `span` 现在填不满——证据链到"那份 PDF"就断了。要页级证据必须先加一层存储（新合规面），本期不做。
2. **现在被挡的人**：仅缺年限 110、仅缺学历 52、两者都缺 19 = **181/277（65%）**。只有 96 人可评估，`candidate_role_fit` 的 192 行正是这 96 人撑的。
3. **`candidate_abox` 与表已不一致**：`check_abox_sync` 现在 14 项 FAIL（装机时 14/0）。`abox.ttl` mtime 07:46 晚于装机 07:44 —— 改过 ABox 没重算。**任何结论在重算前都是旧数。**
4. **`role_` 前缀不一致**：`candidate_role_fit.role` 存裸名，其余三表存 `role_<岗位>`。按 role join 会静默返回 0 行。

## 五、词表路线（本轮新定）

**先抽取、后概括**：从这 10 份 JD 的资格段抽出全部要求词 → 归并同义 → 升成类别 → 再与 ESCO / O*NET / 国标对表补齐。

**否掉的路线**：先拿通用词表往下套。实测证据：现有 29 条手写正则对 10 份 JD 的 44 个要求词只覆盖 **6 个（14%）**。

**外部标准定位**（不是替代，是补齐与背书）：
- 骨干：ESCO（SKOS 本体形态，无中文）+ O*NET（**Tools & Technology** 才是 AutoCAD/SolidWorks/ERP 这类产品名的家）
- 中文别名层：必须自建（CV 写"制图软件"，标准写 `Computer aided design CAD software`）
- 背书：向中国客户解释时，人社部体系（职业分类大典 / 国家职业技能标准）最强
- schema.org **不是**技能分类，只是发布格式

**词表必须是可增补的数据，不是代码里的常量**——证据：「AI工具」已出现在 2 份 JD 里，2020 年的制造业词表不会有它。

## 六、D11 —— 两个真源（stage 之后发现，必须定）

岗位要求同时存在于 公理（`reasoning.ttl`）与 `requirement` 表，**两者都能独立判定谁合格**。
实测：公理给 204 人、闸门给 299 人，**交集只有 38 人（一致率 13%）**。

推荐 **选项 C：分层** —— 公理只做必要条件（`:Candidate ⊓ ∃hasSkill.(该岗位类别 OR)`），
`requirement` 表做覆盖率闸门、tier、年限/学历评分与 unknown 标记；
**两者皆过才算 qualified，分歧必须显式披露**。

C 的唯一必要改动：**从公理里删掉 `∃yearsExperience` 与 `∃educationRank` 两个 facet**
（这正是 D10 的落实）。改后交集从 38 升到 213。

详见 `work/talent/D11_two_sources_of_truth.md`（含三个选项的完整后果与实测表）。
