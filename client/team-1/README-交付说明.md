## 一、这是什么

集团需要一个「会议决议闭环管理系统」，把四个厂区（HQ 总厂 / SW / OS / NB 越南）的会议从「开了就散」变成「事事有决议、件件有闭环」。

现有情况是两套系统各自运转：

```
平台 A（会议管理平台）              平台 B（本次要做的系统）
录音 → 自动转写 → 纪要全文    ──→   会议 + 议题 + 决议事项 + 责任人 + 闭环
（已有，负责语音）                  （新建，负责闭环与分析）
```

历史数据已经跑过一轮：全年 2200 场会、3562 条决议、约 21938 人时。但现有平台是一个单文件 HTML，数据存在各人浏览器里，权限写在前端 JS 中——**无法给多人使用，也无法作为管理依据**。本次是重写，不是改。

## 三、五个必须先知道的技术约束

1. **权限必须在服务端**。原型把权限判断写在前端 JS 里，改一行就能看全集团。新系统每个数据访问方法都必须强制接收数据范围参数（厂区 / 部门 / 本人），越权返回空集而不是报错页——报错页会泄露「这里存在数据」。
2. **所有聚合在服务端算**。前端不持有全量数据。否则「集团总览」和「分厂视图」会出现两个不同的数字，一旦对不上，整个系统就失去信任。
3. **数据接入用快照模型**。每次同步生成不可变快照，事务内切换；失败沿用上一份。不要做增量 upsert——源系统的记录会被人工改，增量同步迟早对不上。
4. **AI 审核是规则引擎，不是大模型**。评分规则是「人 40 + 事 60（正确 / 逻辑 / 重复各 20）」，必须可复算、结论落库。**不要换成 LLM**——同样的数据两次跑出两个分，这个指标就废了。
5. **时区统一 `Asia/Shanghai`**，数据库用 `timestamptz`，不要存本地时间字符串。

## 四、数据现状（这部分会决定你们的工作量）

从 3562 行真实数据里测出来的六个事实，请务必先看：

| 事实 | 数字 | 影响 |
|---|---|---|
| 完成率无区分度 | 98.7%，超期率 3.7% | 现有 KPI 全绿，等于没有指标 |
| 完成时间≈计划时间 | 1349 条中 1288 条同日（95.5%） | 这是自报完成，不是真闭环 |
| 纪要只有一行字 | 中位数 4 字，45.4% 是「无」 | **无法做语义分析**，只能结构化统计 |
| 无责任人 | 1634/3562 = 45.9% | 责任落不下去，需归口到主导人部门 |
| 会议极度集中 | 「计划会议」763 场，占 35% | 这才是真正的洞察点 |
| 时间只覆盖 9 个月 | 2026-01~09，10~12 月仅 14 条 | 「近 12 个月」实际是 9 个月 |

另外：会议类型有 14 种原始标签，其中 `例会/工作汇报`、`例会/临时会议` 是组合式标签（下拉无法单选造成的），必须归一化。`面试`（148 场）、`接待客户`（39 场）根本不是会议，混在时长与人时里会算错账——归一化表见 `01` 文档 2.5 节。

## 五、需要 IT 确认的三件事

这三件事不定，任务 14 之后的部分动不了：

1. **平台 A 的纪要全文怎么拿**：接口、导出文件，还是数据库只读账号？有没有稳定的**会议唯一编号**（比「会议名称 + 日期 + 厂区」匹配可靠得多）。目前方案是先接现有导出字段，接口位置预留，未配置时降级不影响使用。
2. **组织架构从哪来**：继续用静态名单 + 别名规则（现有 177 人 + 37 条别名），还是接 HR 系统接口？别名规则这块必须保留——源数据里「责任部门」经常空着，要靠人名反查部门。
3. **部署环境**：内网单机（目前按 250 账号 / 峰值 30 并发设计）是否足够？如果车间班组长也要用，用户数会到 800+，架构要重新评估。

## 六、技术选型（已确认）

- 后端：Python 3.12 + FastAPI + SQLAlchemy + PostgreSQL 16
- 前端：React 18 + TypeScript + Vite
- 部署：内网单机，一条命令启动，数据库迁移自动执行

## 七、交付节奏

19 个任务分成 6 个切片，**每片可独立上线**：

| 片 | 内容 | 上线后能做什么 |
|---|---|---|
| 1 | 登录 + 权限 + 导入 + 集团总览 | 看到真实会议人时与五个核心指标 |
| 2 | 分厂 + 会议明细 + 十维下钻 | 厂长能看本厂，能钻进每场会 |
| 3 | 闭环引擎（佐证四件套 + 审核 + 结案） | 决议能真正结案，不再是自报 |
| 4 | 统计分析 + 主体成绩 | 回答「会议多好还是少好」 |
| 5 | 知识库 + 重复议题识别 | 同一问题第 N 次上会能被认出来 |
| 6 | 预警 + 导出 + 配置 | 能提醒、能带走、能调参 |

灰度顺序：HQ（占 88% 数据，先压测）→ SW → OS → NB（空态占位）。

上线后 3 个月，新旧口径并行、不混算。

## 八、验收标准（上线 3 个月后回看）

1. 无责任人事项占比从 45.9% 降到 **< 10%**
2. 重复议题识别覆盖 **≥ 80%** 的已知重复问题（人工抽样 50 条核对）
3. 四个视图（集团 / 分厂 / 维度 / 明细）同一指标的数字差异为 **0**
4. 任一角色越权访问返回空集的比例 **100%**
5. 平台 A 接口同步成功率 **≥ 99%**，失败自动降级不阻断
