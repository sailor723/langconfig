# Knowledge-base migration

The knowledge base is **filesystem-only**. Its documents and their `.kvmeta` catalog are the
whole of it, so copying a directory is copying a knowledge base, and no storage mode or settings
document can change that.

```bash
bash migrate_kb.sh                                 # diagnose, write nothing
bash migrate_kb.sh --from /old/data/documents       # diagnose, planning a copy from there
bash migrate_kb.sh --from /old/data/documents --apply
```

## What this touches

| in scope | why |
|---|---|
| `data/documents/project_<id>/` | the documents themselves |
| `data/documents/.kvmeta/project_<id>.json` | the index the Knowledge panel lists from |
| `projects` rows | what makes a project reachable — now created automatically |
| recorded path strings | the absolute paths that dangle once the files move |

Deliberately **out of scope**, so that a knowledge migration can never disturb them:

| out of scope | reason |
|---|---|
| Registry — agents, custom tools, skills, models, directives, settings documents | migrates separately, if at all |
| Workspace — sessions, checkpoints, `workspace_files`, memories, logs | not knowledge; can be large |
| `data/documents/project_chat_sessions/` | chat attachments keyed by session id, not a project |
| `storage_objects` table | skills and agent outputs only; not knowledge |
| RAG index and embeddings | regenerated by re-indexing |

Embeddings live in Postgres (pgvector), so **search does not travel**. A migrated knowledge base
lists and opens immediately; searching it again needs a re-index or a re-upload.

## The procedure

**1. Inventory.** `bash migrate_kb.sh` runs `audit_local_data.py` and reports the documents root,
every project folder, and every folder that has no row. Run it on the old install first.

**2. Copy.** `--from <old documents dir>` copies each numeric `project_<id>/` folder and each
`.kvmeta/project_<id>.json`. `project_chat_sessions` is skipped by rule, and journals are never
copied — a stale `relocate-journal.json` or `adopt-journal.json` from another machine is worse
than useless. Each project's file count is compared before and after, and the run stops if they
differ: an empty folder with an intact catalog passes every later check, so without that guard a
silent copy failure gets adopted as a project with no documents in it.

**3. Rewrite recorded paths.** `relocate_knowledge_paths.py` — `.kvmeta` records hold **absolute**
`storage_path` values, so after any move they name the machine the documents came from. It rewrites
the prefix, verifies per file, journals every change, and is a dry run unless `--apply` is passed.

> While the old tree is still on disk its paths still *resolve*, and paths that resolve are never
> rewritten — by design, so a tree that never moved needs nothing. The consequence is that the
> panel would keep serving documents from the old tree. `migrate_kb.sh` counts records still
> pointing into the source and says so. Delete or move the source, then re-run.

**4. Project rows — automatic.** A project folder found on disk with a `.kvmeta` catalog beside it
is registered the moment the panel asks for the project list (`GET /api/projects/` calls
`services/kb_discovery.register_missing`). There is no step to run and nothing to remember: copy
the folder, and the knowledge base is there.

The row it creates carries every field `ProjectResponse` requires — `status`, `configuration` and
`indexing_status` — because a row of only `id` and `name` makes the endpoint return 500 for *every*
project. The id sequence is advanced past the highest registered id, so the next project created in
the UI does not collide. `scripts/adopt_orphan_projects.py` still exists for scripted use, and is
now normally a no-op.

**5. Verify.** `migrate_kb.sh` re-runs both checks in report mode and exits non-zero unless every
path resolves and every folder has a row. The last check needs a browser: **open a document** in the
Knowledge panel. Listing reads the catalog; opening reads the file.

Then rename the projects — a registered row is named from the folder (`project 16`), which is all
the disk knows.

## Reversal

```bash
backend/scripts/relocate_knowledge_paths.py --rollback   # restores every path from its journal
backend/scripts/adopt_orphan_projects.py --undo          # removes rows the explicit tool created
```

Both are exact. **No step here ever deletes or moves a document.**

## Traps worth knowing

- **`cp -a src/ dest/` is not portable.** BSD cp (macOS) with a trailing slash on the source copies
  its *contents*, flattening every document into the documents root; GNU cp (Ubuntu) creates
  `dest/src`. Same command, two different trees, both reporting success. `migrate_kb.sh` copies
  into a directory it names itself.
- **The storage mode used to gate all of this, and no longer does.** In `db` mode the panel listed
  documents from `storage_objects` in Postgres, so a copied folder was present and invisible. The
  knowledge base no longer reads the database to find or list itself.
- **The settings document cannot repoint the knowledge base.** The root comes from environment
  configuration (`KB_ROOT`, then `DOCUMENTS_BASE_DIR`, then `./data/documents`), resolved by
  `services/kb_discovery.kb_root()`. If a `storage.documents_base_dir` in the database disagrees,
  `audit_local_data.py` reports it and nothing obeys it.
- **Re-uploading is not a failure mode.** For a small knowledge base it is the cheapest correct
  migration: the UI creates the project row and indexes the documents as they arrive.

## Verified

`backend/scripts/verify_copied_knowledge_base.py` asserts this contract through the real routes
against a scratch database and a scratch documents tree — 10/10, including that a copied folder is
listed with no operator action, that a storage settings document pointing at a nonexistent path
with `mode='db'` has no effect, and that a project created afterwards does not collide.
