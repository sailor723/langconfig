# Knowledge-base migration

Moving a knowledge base between installs, and nothing else. Written to be run without knowing
anything about the rest of the system.

```bash
bash migrate_kb.sh                                 # diagnose, write nothing
bash migrate_kb.sh --from /old/data/documents       # diagnose, planning a copy from there
bash migrate_kb.sh --from /old/data/documents --apply
```

## What this touches

| in scope | why |
|---|---|
| `data/documents/project_<id>/` | the documents themselves |
| `data/documents/.kvmeta/project_<id>.json` | the index the Knowledge panel lists from |
| `projects` rows | what makes a project reachable at all |
| recorded path strings | the absolute paths that dangle once the files move |

Deliberately **out of scope**, so that a knowledge migration can never disturb them:

| out of scope | reason |
|---|---|
| Registry — agents, custom tools, skills, models, directives, settings documents | migrates separately, if at all |
| Workspace — sessions, checkpoints, `workspace_files`, memories, logs | not knowledge; can be large |
| `data/documents/project_chat_sessions/` | chat attachments keyed by session id, not a project |
| `storage_objects` table, RAG index, embeddings | unused in `local` mode; regenerated by re-indexing |

Embeddings live in Postgres (pgvector) whatever the storage mode, so **search does not travel**.
A migrated knowledge base lists and opens immediately; searching it again needs a re-index or a
re-upload.

## Prerequisite: storage mode must be `local`

Two values, and only these two, are recognised: `local` and `db` (`api/system/settings.py:359`).
If `docs/TEAM_MIGRATION.md` says `fs`, that works only by accident — anything that is not `db`
falls through to local behaviour.

```bash
cd backend
.venv/bin/python -c "from config import settings; print(settings.storage_mode)"
```

`migrate_kb.sh` reports the mode from both places and warns if either says `db`, because in `db`
mode `api/knowledge/kv.py:377` lists documents from `storage_objects` in Postgres instead of from
`.kvmeta` on disk — a copied folder then does not appear, however complete it is.

The two sources are not the same setting. `.env`'s `STORAGE_MODE` is the bootstrap default; the
Settings → Storage choice is persisted in the storage document and applied over it at startup by
`main.py:106-108`. Standalone scripts never run `main.py`, so they see only `.env`. Set both to
`local` and the question disappears.

## The procedure

**1. Inventory.** `bash migrate_kb.sh` runs `audit_local_data.py` and reports the documents root,
every project folder, and which folders have no row. Run it on the old install first to decide
what is worth copying.

**2. Copy.** `--from <old documents dir>` copies each numeric `project_<id>/` folder and each
`.kvmeta/project_<id>.json`. `project_chat_sessions` is skipped by rule. Journals are never
copied: a stale `relocate-journal.json` or `adopt-journal.json` from another machine is worse than
useless.

Each project's file count is compared before and after the copy and the run stops if they differ.
An empty folder with an intact `.kvmeta` record passes every later check in this script, so
without that guard a silent copy failure gets adopted as a project with no documents in it.

**3. Rewrite recorded paths.** `relocate_knowledge_paths.py` — the `.kvmeta` records hold
**absolute** `storage_path` values, so after any move they name the machine the documents came
from. It rewrites the prefix and verifies per file, journals every change, and is a dry run unless
`--apply` is passed.

> While the old tree is still on disk its paths still *resolve*, and paths that resolve are never
> rewritten — by design, so a tree that never moved needs nothing. The consequence is that the
> panel would keep serving documents from the old tree. `migrate_kb.sh` counts records still
> pointing into the source and says so. Delete or move the source, then re-run.

**4. Create the missing rows.** `adopt_orphan_projects.py --apply`. The panel lists projects from
`GET /api/projects/`, and a copied folder has no row, so the documents are present and unreachable
— this is the failure that stalls most migrations. It inserts the full row (`ProjectResponse`
needs `status`, `configuration` and `indexing_status`, or the whole project list returns 500) and
advances `projects_id_seq` past the highest adopted id, because explicit ids do not advance it and
the next project created in the UI would collide.

Order matters: `doctor.sh` refuses to adopt while anything dangles, so step 3 precedes step 4.

**5. Verify.** `migrate_kb.sh` re-runs both scripts in report mode and exits non-zero unless every
path resolves and every folder has a row. The last check needs a browser: **open a document** in
the Knowledge panel. Listing reads the index; opening reads the file.

Then rename the adopted projects — their names come from the folder (`project 16`), which is all
the disk knows.

## Reversal

```bash
backend/scripts/relocate_knowledge_paths.py --rollback   # restores every path from its journal
backend/scripts/adopt_orphan_projects.py --undo          # deletes the rows --apply created
```

Both are exact: relocate restores previous values, undo removes only the ids it created and only
while they still carry the adopt marker, so a project a human has since taken over is left alone.
**No step here ever deletes or moves a document.**

## Traps worth knowing

- **`cp -a src/ dest/` is not portable.** BSD cp (macOS) with a trailing slash on the source
  copies its *contents*, flattening every document into the documents root; GNU cp (Ubuntu)
  creates `dest/src`. Same command, two different trees, both reporting success. This script
  copies into a directory it names itself.
- **`fs` is not a value.** Use `local`.
- **`doctor.sh` is the same diagnosis, narrower view** — it is the two checks in steps 3 and 4.
  `migrate_kb.sh` adds the copy and the verification.
- **Re-uploading is not a failure mode.** For a small knowledge base it is the cheapest correct
  migration: the UI creates the project row and indexes the documents as they arrive, so none of
  the above applies. Reserve the copy route for what is too large to re-upload.

## Verified

`backend/scripts/verify_copied_knowledge_base.py` reproduces the copied-KB case against a scratch
database and a scratch documents tree, asserts it is genuinely broken, applies the fix, and
asserts it is genuinely fixed — 8/8, including that a project created afterwards does not collide
with an adopted id.
