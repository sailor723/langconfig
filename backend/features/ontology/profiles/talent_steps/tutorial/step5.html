What we add

One concrete skill, filed under a category

:Python  a  :SkillTag , :Programming .

:Programming  a  owl:Class ;
    rdfs:subClassOf :SkillTag .

In plain words

“Python” is one specific skill — a particular thing, like a name on a list. It goes in the skills box, and it is filed as a programming skill (rather than, say, a spreadsheet skill).

So after this step you can point at one skill and say what kind of skill it is:

:Python  →  a specific skill  →  of kind "programming"

This is the shape the whole ontology uses: the specific thing and the kind of thing, kept apart on purpose. Step 7 needs both — the rule will say “has a programming skill”, and the machine has to recognise Python as one.

Why this is next

The box has been empty for two steps. Now we put something in it.

What the reader sees

One item inside the skills box, and a narrower box it also belongs to.

Optional technical note

:Python is an individual (one named thing); :Programming is a class (a category, ⊑ :SkillTag). One sentence gives the individual two types — which is why it is written with a comma:

:Python  a  :SkillTag , :Programming .
                   ↑            ↑             ↑
        “Python IS …”   the kind    also the kind
                        of skill    it belongs to

Which side is this on — the rules, or the facts?

This step writes two kinds of sentence at once, and they belong to different halves of the ontology:

:Python  a  :SkillTag , :Programming .      ← a FACT
:Programming  a  owl:Class ;                ← a RULE
              rdfs:subClassOf :SkillTag .
The facts (ABox)The rules (TBox)
Talks aboutparticular thingskinds of things
Subject isa named individuala class, a property, an axiom
Here:Python:Programming, :SkillTag
Changes whennew data arrives (a new CV)the rules change (rarely)

The left-hand name decides, not the file it sits in: :Python on the left is a fact; :Programming on the left is a rule.

Optional technical note

Why the split matters mechanically: the rule in step 7 points at the class (someValuesFrom :Programming), and the fact points at the individual (:Python a :Programming). The reasoner needs that bridge — the fact is how a person who has Python reaches a rule about Programming. No bridge, no conclusion.

The mistake this course exists to prevent

Wrong

:Python  a  owl:Class .     ← WRONG

Written as a category, “Python” becomes an empty box. Then the rule “has a programming skill” matches nobody at all — there is no thing anyone could have.

Right

:Python  a  :SkillTag , :Programming .

You cannot have a category. You can have a Python. The category is what you reason over; the item is what someone has. This is the rule of thumb for the whole course:

the thing you can have is an individual; the thing you can reason over is a class.

Optional technical note

That one line is the bridge from facts to rules: the reasoner matches an individual whose type is the class, so :Python a :Programming . is what lets “has some programming skill” ever fire.

One question that needs reasoning — not just querying

          
Everything above was a question the files can answer: the answer was
          written down somewhere in the ontology, and a query finds it.

          
Here is a question of a different kind:

          
The question

            
SELECT ?c WHERE { ?c a :matches_SoftwareEngineer }

            
“Who qualifies as a software engineer?”

            
The ontology names this class :matches_SoftwareEngineer — “matches
            software engineer”, in the client's own language. The query above uses the English
            spelling so this page stays in one language; the ontology keeps the Chinese name.

          

          
Run it — in the box above, at any scope, including the whole
          ontology:

Even on the finished ontology, with every fact in place, the query finds
            nothing. And that is not a bug in the query.

          

          
Try it yourself

            
Type that query in the box above and press Run the query — it comes
            back empty. Then press Ask the reasoner (the class is already filled
            in) and watch the same question get an answer.

Ask the reasoner  → cand_A

            
Both buttons ask the same question of the same ontology. The only
            difference is which tool answers it — and that is the whole point of this step.

          

          
WHY it cannot answer it — the three reasons

            
#ReasonIn the ontology

              
1
                  The rule does not exist yet. A query can only find answers
                      that were written down. Nobody has written down what “qualifies” means.
                  There is no axiom until step 7 — no
                      owl:equivalentClass anywhere in the file.

              
2
                  Even with the rule, the answer is not in the file. The rule
                      says who should qualify; it does not say who does. Nobody
                      ever writes “cand_A qualifies”.
                  :cand_A a :matches_SoftwareEngineer appears in
                      no file — writing it would be the answer, and the answer is
                      what we want the machine to produce.

              
3
                  SPARQL matches; it does not conclude. A pattern matches
                      triples that already exist. To get an answer that does not exist yet, something
                      has to infer it — and that is the reasoner's job, not the
                      query's.
                  SPARQL asks “is this triple there?”; the reasoner asks “must this triple be
                      true, given what I know?”

            

            
Reasons 1 and 2 are about the ontology. Reason 3 is about the
            tools — and it is the one that matters most, because it stays true even when
            the ontology is perfect.

          

          
This is what step 7 is for

            
Step 7 writes the rule, and the reasoner applies it. After that, the
            same question has an answer:

            
via SPARQL on the files        → no rows
via the REASONER on the same file → cand_A

            
Both looked at the same ontology. One found nothing, the other found the
            answer. The difference is that the reasoner concludes and a query only
            looks.

            
The platform shows this side by side: its SPARQL endpoint runs every
            query twice — once over the asserted graph, once over the graph plus the inferred
            types — so a reader sees the 0 → 1 transition instead of being told
            about it.
