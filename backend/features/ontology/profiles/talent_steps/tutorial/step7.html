What we add

The definition of “software engineer”

:matches_SoftwareEngineer  a  owl:Class ;
    owl:equivalentClass [
        owl:intersectionOf (
            :Candidate
            [ a  owl:Restriction ;
               owl:onProperty    :hasSkill ;
               owl:someValuesFrom :Programming ]
            [ a  owl:Restriction ;
               owl:onProperty    :yearsExperience ;
               owl:someValuesFrom [ a rdfs:Datatype ;
                                    owl:onDatatype xsd:integer ;
                                    owl:withRestrictions ( [ xsd:minInclusive 3 ] ) ] ] ) ] .

In plain words

A software engineer is someone who is a candidate, and has a programming skill, and has 3 years or more of experience.

That is the bar. From here on, nobody types anyone's name into the answer — the machine works it out from the rule and the facts.

Why this is last

Every piece of it must already exist: a candidate (step 1), experience (step 2), skills and their category (steps 3–5), and the link that ties them together (step 4). A rule cannot mention something that is not there yet.

What the reader sees

Nothing new in the file — and that is the point. The answer is no longer written down; it is worked out.

Optional technical note

An equivalent class — a definition. The class must have a name (a owl:Class); without it the reasoner answers “this class is not in the ontology”. And someValuesFrom points at the category :Programming, not at the bare :SkillTag — otherwise every skill would match.

Nobody wrote this down

          
:cand_A a :matches_SoftwareEngineer .     ← NEVER write this

          
The rule says it and the machine works it out. To prove the machine worked it out —
          rather than us having typed it — delete the rule and run it again:

          
before deleting the axiom : matches_SoftwareEngineer → cand_A
after  deleting the axiom : matches_SoftwareEngineer → []

          
The answer disappears with the rule. That test is the difference between a
          system that describes and one that decides.

        

        
How is this different from a plain SQL query?

        
Same question, two ways of asking it. A SQL query states the question:

        
SELECT c.name
FROM candidate c
JOIN candidate_skill cs ON cs.candidate_id = c.id
WHERE cs.skill_id IN (SELECT skill FROM skill WHERE category = 'Programming')
  AND c.years_experience >= 3;

        
The ontology states the rule, and gives the answer a name:

        
:matches_SoftwareEngineer  ≡
      :Candidate
   ⊓  ( :hasSkill       some :Programming )
   ⊓  ( :yearsExperience some xsd:integer[>=3] )

        
Both answer “who qualifies”. Three differences matter in daily work:

        
A SQL queryThe ontology

          
Where the rule lives
              copied into every query that needs it
              written once, as the definition of a named class

          
The bar changes from 3 years to 5
              hunt down every saved search, dashboard, report and job that hardcoded
                  >= 3 — and they drift apart
              change one line; every consumer of
                  matches_SoftwareEngineer changes with it

          
Where the answer is
              a row in a table — something to refresh, and to go stale
              nowhere: it is computed on demand, so it cannot be stale

        

        
The one that bites: “filed by years of experience”

          
Your question was exactly right. In SQL, years_experience >= 3 is
          copied into every query that filters on experience. Five queries, five copies, and
          when the bar moves you have to find all five — the ones somebody forgot are now quietly
          wrong.

          
In the ontology the bar is one fact about the role. It is not written
          into the queries at all: a query asks for matches_SoftwareEngineer, and the
          rule brings the years condition with it.

        

        
Where the ontology stops

          
It is not a replacement for SQL — it is a different layer. The ontology decides
          who qualifies and gives that answer a name; SQL does what you do with those
          people (totals, rankings, exports). Questions that need an aggregate are SQL's job.

          
On this project the two are literally joined: the ontology's classes are
          compiled into SQL (a definition becomes a WHERE clause), and the metrics are
          computed over that. The definition is written once.

        

        
Why the reasoner choice matters

        
HermiT vs ELK / OWL 2 RL

          
ReasonerThis axiomWhy

            
HermiTconcludes cand_A
                it can decide the “3 years or more” threshold

            
ELK / OWL 2 RLconcludes nobody
                OWL 2 RL does not decide numeric limits

          

          
The weaker reasoner gives an empty answer — which reads as
          “nobody qualifies”, not “the tool cannot judge this”. Recruiting decisions are mostly
          thresholds, so this course must use HermiT.
