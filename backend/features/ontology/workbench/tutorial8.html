A second object, but of a different kind: nothing is a store in a report — a store is something orders are attributed to. It has no measure at all, only the dimension every city metric groups by.

The link: an order was sold at a store

a many-to-one link — so a column is enough

link:Order —sold at→ :Store
cardinalitymany-to-one (many orders per store, one store per order)
carriesnothing — the link has no data of its own
stored inorders.sold_at (one FK, no extra table)
Compare with step 7: a many-to-many link that carried qty needed a table of its own (reification). This link is many-to-one and carries nothing, so a single foreign key on the order row is enough — cardinality and payload decide the storage shape, not habit.

A dimension, not a measurement

cityordersrevenue
The numbers above are sums of orders. The city next to each sum is never summed — it is the key the metric groups by, and it lives on another object. That is the whole job of a dimension: it divides a measure, it never adds to one.
Which is why “revenue by store” is not a declared metric: a store has no name property to group on here, only a city. The ontology says what can be a key, and the query layer refuses the rest by name.

The ontology says


        
One declared edge is all this link needs:
          orders.sold_at → stores.id, with :references :Store naming the
          target. The metric then reads :city off that object and groups by it — the
          compiler never guesses that sold_at is a store, it reads the declaration.
          Adding the premium filter rides on the same machinery: :where :PremiumCustomer
          compiles to a WHERE predicate, not to hand-written SQL.
