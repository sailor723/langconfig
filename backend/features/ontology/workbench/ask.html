SPARQL — lane B (Ontop over the virtual RDF graph)

The map search on the main page only filters words. This box runs real queries: lane B answers `Customer` even though the data never stored it — subclass entailment inside OWL 2 QL. The HermiT demo shows the answer that only a DL reasoner can produce (owl:hasValue).

Lane C guard — would this action be admitted? (dry-run, no write)

PromoteCustomer's guard is compiled from the :PremiumCustomer axiom — the same definition lane A/B use. This runs the compiled preconditions in a transaction that is always rolled back, so it answers “admitted or refused, and why” without writing and without an audit row.

What to expect

ASK { <…/customer/1> a ex:Customer } → true — entailed, never stored.
SELECT ?c WHERE { ?c a ex:Customer } → 4 rows (includes the 2 PremiumCustomers).
SELECT ?c ?n WHERE { ?c a ex:PremiumCustomer ; ex:name ?n } → Dana Okafor, Chen Hong.
HermiT demo: before-reasoning query is empty, after-reasoning it lists customer_1 and customer_3 — the fact derived from PremiumCustomer ≡ Customer ⊓ hasTier value tier_PREMIUM, which Ontop cannot rewrite (not OWL 2 QL).
Guard dry-run: PromoteCustomer on customer 2 → ADMITTED, with the parameters BOUND (… WHERE id = 2 AND NOT (tier = 'PREMIUM')) and the target row shown as Bob Smith · STANDARD; on customer 1 → REFUSED and the failing check names the axiom. Nothing is written, no audit row appears — the dry-run is the read of what the write would do. The Run it for real button executes the same params through lane C: one transaction, an audit row, and the guard is re-checked on the same target so you watch it flip to REFUSED.
