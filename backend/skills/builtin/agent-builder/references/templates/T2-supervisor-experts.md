# T2 · supervisor + 专家

> 提炼自：案例 4（323）、案例 6（301）、案例 9（320）· 事实见 `references/facts/case-facts.md`

## 1 适用场景

用：任务横跨几个明确领域，每个领域的工具集不同，且每个专家的结果**一两句话就能带回来**。
**不要用**：一个专家的输出是文件而不是摘要（→ T5）；按阶段推进、每次只做一个动作（→ T3）。

判据一句话：**主 agent 的职责是"选人 + 汇总"，不是"干活"**。它自己不该有业务工具。

## 2 配置骨架

```json
{
  "name": "{{slug}}",
  "kind": "normal",
  "category": "{{category}}",
  "description": "{{一句话}}",
  "temperature": 0.0,
  "native_tools": ["task"],
  "skills": [],
  "subagents": [
    {
      "name": "{{expert_a}}",
      "description": "{{什么时候派给它 —— 这句决定路由成败}}",
      "system_prompt": "{{专家自己的提示词：只做这一件事，做完一句话回报}}",
      "tools": ["{{tool_a}}"],
      "middleware": [],
      "interrupt_on": {}
    },
    {
      "name": "{{expert_b}}",
      "description": "{{...}}",
      "system_prompt": "{{...}}",
      "tools": ["{{tool_b}}", "{{tool_c}}"],
      "middleware": [],
      "interrupt_on": {"{{写外部的工具}}": {"when": "writes_deliverable", "allowed_decisions": ["approve", "reject"]}}
    }
  ],
  "middleware": [],
  "system_prompt": "{{见第 3 段}}"
}
```

**关键**：`native_tools` 只写 `["task"]`。三个案例（301/320/323）都是这一个工具——
委派面就是这一个，别给主 agent 再配业务工具，否则它会自己抢活干。

## 3 提示词骨架

主 agent（案例 4 的写法，5,187 字里去掉重复后剩下的骨架）：

```
你是 {{主角色}}，负责分派和汇总。你自己不执行业务动作。

## 分派规则
- {{领域 A 的说法}} → {{expert_a}}
- {{领域 B 的说法}} → {{expert_b}}
- 一句话里有两件事：分别派给两个人，再合并成一段回答

## 汇报
- 每个专家的回报 ≤ {{N}} 行；细节留在专家那边
- 合并时按用户问的顺序写，不要按专家顺序

## 边界
- 不属于任何专家：直接说没有这个能力，不要硬凑
```

专家（每个 3–5 行就够）：

```
你是 {{专家名}}。只做 {{一件事}}。
用 {{工具}} 完成；做完用 ≤3 行回报：结论 + 关键数字 + 来源。
不要解释过程，不要写文件（除非任务要求）。
```

## 4 工具与 middleware

| 项 | 必选 | 说明 |
|---|---|---|
| 主 agent 工具 | **只有 `task`** | 三个案例一致 |
| 专家工具 | 每个 1–3 个 | 案例 6 的专家各 1 个工具，最干净 |
| 专家 `description` | 必填且具体 | 路由靠它，不靠提示词列举 |
| `interrupt_on` | 写外部（发信、写库）时挂 | 案例 4 的 `email_expert` 这么做 |
| 主 agent `hitl` | 要看住派活时挂 | 注意：**父的 `interrupt_on` 管不到子代理内部**，要拦子代理自己的工具得写进子代理的 `interrupt_on` |

## 5 rubric 模板

```
R1 分派正确：问 {{领域 A 的问题}}，tool sequence 里出现 task，且回报内容来自 {{expert_a}}
R2 不抢活：主 agent 没有直接调用业务工具（tool sequence 里没有 {{tool_a}}）
R3 合并：一句话里含两个领域时，回答同时覆盖两件事
R4 审批：{{外发动作}} 触发审批卡，拒绝后没有产生外部副作用
```

## 6 实测基线

- 案例 6（301）：`task` 一轮里发出两个并行调用（`weather_expert` + `math_expert`）
- 案例 9（320）：与 301 结构同形，差别只在提示词的分派策略（并行 vs 按需）
- 案例 4（323）：日历探针 44–70s，`task` + 13 个 MCP 工具

## 7 失败对照

| 症状 | 原因 | 改法 |
|---|---|---|
| 主 agent 自己答了 | 提示词没禁止，或它有业务工具 | 工具只留 `task`，第 3 段写"你自己不执行业务动作" |
| 派错专家 | 专家 `description` 太笼统 | description 写"什么时候派给我"，不写"我是什么" |
| 专家回报一大段 | 没约束行数 | 专家提示词写"≤3 行回报" |
| 审批不弹 | 拦的是父 agent | 写进子代理的 `interrupt_on`，或改用 T3 |
