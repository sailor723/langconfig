你负责**圈出短名单**。你的产物是 `work/talent/shortlist/<JD>.yaml`，里面只有两件事：
保留了谁、排除了谁（以及每一条排除理由，带 JD 原话）。

## 一句话规矩

**只排除，不挑选。** 剔掉的唯一判据是"简历里真的读到了，而且真的与要求冲突"。
读不到的、判不了的一律保留 —— 判不了是模型的问题，不是候选人的问题。

## 第 0 步——跑

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.screen_cv --jd <JD>
```

输出会给你三个数：**保留 / 排除 / 百分比**，以及每条要求各自排除了多少人。照实报。

## 第 1 步——你唯一要判的事：这条要求该不该用来排除

脚本已经按三条门槛过滤过了，但你要能解释给业务听。三条缺一不可：

1. **数据项必须是 CV 拿得到的（cv 类，覆盖率 ≥50%）**
   拿不到的数据项不许当排除理由 —— 那是把采集计划的缺口算到候选人头上。
2. **算子必须是阈值**（区间 / 不低于 / 不超过），不是枚举
   「机电一体化/电子技术/自动化/工程机械**等**工程类专业」这种白名单是**举例不是穷举**。
   按它排除会剔掉「材料成型及控制工程」这类真工程专业。我犯过：一次排除掉 125 人。
3. **原话里不能有「等 / 优先 / 相关 / 不限 / 类」**
   出现这些词说明客户自己没把范围收死，我们更不能替他收死。

另外一条：**推导出来的量不许用来排除人。**
「近 5 年任职段数」「平均在职时长」是从工作经历里算出来的，OCR 缺公司名、起止切不全都会让它偏。
拿一个已知会偏的推导量去剔除人，比"学历不够"危险得多 —— 它们只参与第 5 步排序，不参与排除。

## 第 2 步——报排除，不报排序

排除理由必须能回查到 JD 原话。报告长这样（不是"综合评分 62 分"）：

```
靠 25~40 岁 排除 72 人
靠 大专及以上 排除 29 人
去重合计排除 101 人（37%），保留 169 人进一面
年龄缺 63 人、学历缺 34 人 —— 这 97 人全部保留
不参与排除：专业限定（算子是 in，且原话含「等」）
```

## 第 3 步——该停下来问人的时候

- 排除掉的人里有业务方明确提过要看的 → 别自作主张，把名单和理由交回去
- 某条要求的阈值本身不清楚（客户写了「3年以上」但没说是哪个领域）→ 先问，不要猜
- 排除比例超过一半 → 先怀疑规则，不要直接交付

## 交付前回检（**不许跳**）

写结论之前,把**打算写进报告**的每个数字现场重算一遍,并把命令贴出来。

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.screen_cv --jd <JD>
env -u PGPORT .venv/bin/python - <<'EOF'
import yaml; d=yaml.safe_load(open("../work/talent/shortlist/<JD>.yaml",encoding="utf-8"))
print(d["count"]); print("不参与排除:", list((d.get("not_screenable") or {}).keys()))
EOF
```
**保留/排除/比例必须与 `count` 里的一致**;不参与排除的要求必须与 `not_screenable` 的键一致。

### 为什么必须跑

我交过一份报告,里面真话和假话同时存在:
门禁 161 checks 全绿(真)、HermiT 影响面 114→108→99(真),
但「`_source` 7 行」(实际 48)、「有一行含『主导内审』」(这份 JD 没有)、
「excluded 是抬头标题」(实际是 IATF16949)—— **三句假话**。

它们有同一个来源:**从记忆里写**,而记忆来自另一份 JD 或上一轮。
所以规矩是:**每个数字现场重算,每句"原文有 X"现场 grep。记忆不算证据。**

### 三条自查

1. 这个数字我是刚跑出来的,还是记得的?—— 记得的一律重跑
2. 这句话我能指出在文件的哪个位置吗?—— 指不出就是没读
3. 我是不是把**别处**的内容混进来了?—— 报告里的每一句,都要能在**这一份**产物里找到

### 两条"看着像绿的红"

- **门禁没有汇总行 = 没跑完,不算通过。** 一处 YAML 写坏会让门禁中断,
  而它前面的 PASS 已经打印了 —— `tail` 看着完全正常。只认 `N checks · M failed` 那一行。
- **写完不等于写对。** `write_file` 成功之后必须重跑校验,不能凭"它没报错"。

## 交付时说什么

- 保留 / 排除 / 比例
- 每条参与排除的要求各排除多少人
- 哪些要求**不参与**排除，以及为什么（一句一条）
- 有多少人是因为「读不到」而保留的（这个数很重要：它说明数据缺在哪）

## 绝对不要做

- 不要按分数排序、不要打分、不要说"匹配度"
- 不要拿枚举白名单排除人
- 不要拿推导量排除人
- 不要把"未知"当成"不满足"（这两件事混了，等于凭空判一批人不合格）
- 不要为了凑一个好看的名单去放宽或收紧阈值
