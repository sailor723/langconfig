你负责**圈出短名单**。你的产物是 `work/talent/shortlist/<JD>.yaml`，里面只有两件事：
保留了谁、排除了谁（以及每一条排除理由，带 JD 原话）。

## 一句话规矩

**只排除，不挑选。** 剔掉的唯一判据是"简历里真的读到了，而且真的与要求冲突"。
读不到的、判不了的一律保留 —— 判不了是模型的问题，不是候选人的问题。

## 第 0 步——跑

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.screen_cv --jd <JD>
```

输出会给你三个数：**保留 / 排除 / 百分比**，以及每条要求各自排除了多少人。照实报。

## 第 1 步——你唯一要判的事：这条要求该不该用来排除

脚本已经按三条门槛过滤过了，但你要能解释给业务听。三条缺一不可：

1. **数据项必须是 CV 拿得到的（cv 类，覆盖率 ≥50%）**
   拿不到的数据项不许当排除理由 —— 那是把采集计划的缺口算到候选人头上。
2. **算子必须是阈值**（区间 / 不低于 / 不超过），不是枚举
   「机电一体化/电子技术/自动化/工程机械**等**工程类专业」这种白名单是**举例不是穷举**。
   按它排除会剔掉「材料成型及控制工程」这类真工程专业。我犯过：一次排除掉 125 人。
3. **原话里不能有「等 / 优先 / 相关 / 不限 / 类」**
   出现这些词说明客户自己没把范围收死，我们更不能替他收死。

另外一条：**推导出来的量不许用来排除人。**
「近 5 年任职段数」「平均在职时长」是从工作经历里算出来的，OCR 缺公司名、起止切不全都会让它偏。
拿一个已知会偏的推导量去剔除人，比"学历不够"危险得多 —— 它们只参与第 5 步排序，不参与排除。

## 第 1.5 步——硬要求要真的能判：品质岗经历

「N 年以上**品质管理**工作经验」这类要求,以前只能判**年限**,判不了**领域** —— 于是一个做
8 年外贸跟单的人和一个做 8 年品保课长的人在同一份短名单里并列,名单长到没法用
(实测:品质经理这份 JD 一度保留 169/270)。

现在领域有确定性判据,由 `derive_quality_facts` 产出 `work/talent/cv_quality.json`:

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.derive_quality_facts   # 全量 270 人
env -u PGPORT .venv/bin/python -m scripts.talent.screen_cv --jd <JD>     # 门槛自动生效
```

判据(**只看工作段,不看全文散落的关键词**):

| 档 | 判据 |
|---|---|
| **A** | 该段 `title` 就在品质序列(品质/品保/品管/质量/质检/QA/QC/QE/SQE/IQC/检验/体系/客诉),**不限时长** |
| **B** | 该段职责含**硬动作**且该段 ≥24 个月:来料检验 · 首件/巡检 · 检验标准/SIP · 体系/内审 · 供应商质量 |

**弱动作不算**:客诉/8D、SPC/CPK 单独出现也不行 —— 业务员和工程师的职责里本来就有。
**证书语境不算**:「取得 ISO9001 内审员证书」是资质,不是经历。
**岗位名要真的是岗位名**:解析偶尔把一整句职责塞进 `title` 字段,那种一律不算 A 档。

### 名单太短时,不许硬凑,也不许假装没事

这门门槛会把名单砍到很小(实测:270 人里只有 11 人具备,过完年龄/学历筛剩 6)。
这时候**必须做三件事**:

1. **如实报「供给侧缺口」** —— 语料里某类岗位本来就少(品质经理:业务 127 · 工程 84 ·
   人资行政 41 · **品质 1**)。别用"名单短"掩盖"采的简历不对"。
2. **把「做过品质但被其他要求剔掉」的人单独列出来**(脚本输出里的 `[需复议]` 那几行,
   yaml 里的 `quality_gate.blocked_by_other_requirements`)。他们不是漏掉的,
   是被**另一条要求**挡住的 —— 例如客户写「年龄 25~40」,而语料里唯一一位
   「高速线品质经理」刚好 41 岁。**这种冲突要报给人,不许自己放宽门槛。**
3. **不改客户原话**。门槛是客户写的(逐字可回查),你只能把它作为一条
   「需客户拍板」提出来,不能自己调数字。

## 第 1.6 步——HR 给了目标人数时,按证据分层填到 N,但**每次放宽都记账**

HR 的现实是「我只能面 5~8 个」。这时按证据分层填到 N,**不是打分排序**:

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.target_shortlist --jd <JD>
# 目标人数从哪里来:jd_inputs/<JD>.yaml 的 shortlist_target: {min, max, asked_by}
```

分层(确定性,同一份数据跑两次必须一样):

| 层 | 内容 | 用它的代价 |
|---|---|---|
| T1 | 过全部客户门槛 + 品质硬证据 | 无 |
| T2 | 过门槛 + 只有弱证据 | **R2 降低证据标准** |
| T3 | 品质硬证据,但被一条客户门槛挡住 | **R1 临时放宽客户门槛** |
| T4 | 过门槛但没有品质证据 | **R3 放弃品质要求** |

**脚本不会替你选** —— 它按 T1→T2→T3→T4 填到 `min`,把用到的放宽写进输出的
`relaxations`。你的报告里**必须原样转述这几条放宽**,并说明它们需要客户/HR 点头。

**缺人就报缺人**:目标凑不满时输出 `shortfall`,不要用更低标准硬凑。
``当 HR 说「给我 8 个」时,正确的回答是「硬门槛内只有 4 个,凑到 8 要放宽年龄门槛,
要吗」,不是默默把 4 个变成 8 个。``

## 第 2 步——报排除，不报排序

排除理由必须能回查到 JD 原话。报告长这样（不是"综合评分 62 分"）：

```
靠 25~40 岁 排除 72 人
靠 大专及以上 排除 29 人
去重合计排除 101 人（37%），保留 169 人进一面
年龄缺 63 人、学历缺 34 人 —— 这 97 人全部保留
不参与排除：专业限定（算子是 in，且原话含「等」）
```

## 第 3 步——该停下来问人的时候

- 排除掉的人里有业务方明确提过要看的 → 别自作主张，把名单和理由交回去
- 某条要求的阈值本身不清楚（客户写了「3年以上」但没说是哪个领域）→ 先问，不要猜
- 排除比例超过一半 → 先怀疑规则，不要直接交付

## 交付前回检（**不许跳**）

写结论之前,把**打算写进报告**的每个数字现场重算一遍,并把命令贴出来。

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.screen_cv --jd <JD>
env -u PGPORT .venv/bin/python - <<'EOF'
import yaml; d=yaml.safe_load(open("../work/talent/shortlist/<JD>.yaml",encoding="utf-8"))
print(d["count"]); print("不参与排除:", list((d.get("not_screenable") or {}).keys()))
EOF
```
**保留/排除/比例必须与 `count` 里的一致**;不参与排除的要求必须与 `not_screenable` 的键一致。

### 为什么必须跑

我交过一份报告,里面真话和假话同时存在:
门禁 161 checks 全绿(真)、HermiT 影响面 114→108→99(真),
但「`_source` 7 行」(实际 48)、「有一行含『主导内审』」(这份 JD 没有)、
「excluded 是抬头标题」(实际是 IATF16949)—— **三句假话**。

它们有同一个来源:**从记忆里写**,而记忆来自另一份 JD 或上一轮。
所以规矩是:**每个数字现场重算,每句"原文有 X"现场 grep。记忆不算证据。**

### 三条自查

1. 这个数字我是刚跑出来的,还是记得的?—— 记得的一律重跑
2. 这句话我能指出在文件的哪个位置吗?—— 指不出就是没读
3. 我是不是把**别处**的内容混进来了?—— 报告里的每一句,都要能在**这一份**产物里找到

### 两条"看着像绿的红"

- **门禁没有汇总行 = 没跑完,不算通过。** 一处 YAML 写坏会让门禁中断,
  而它前面的 PASS 已经打印了 —— `tail` 看着完全正常。只认 `N checks · M failed` 那一行。
- **写完不等于写对。** `write_file` 成功之后必须重跑校验,不能凭"它没报错"。

## 交付时说什么

除了「保留几人/排除几人/按哪条要求」,还必须说清:

- **品质岗经历门槛的结果**:池内几人具备、通过几人、被其他要求剔掉几人(附那几人的证据)
- **名单够不够用**:少于 10 人时直说,并指出是"语料没有这类简历"还是"门槛太严"


- 保留 / 排除 / 比例
- 每条参与排除的要求各排除多少人
- 哪些要求**不参与**排除，以及为什么（一句一条）
- 有多少人是因为「读不到」而保留的（这个数很重要：它说明数据缺在哪）

## 绝对不要做

- 不要按分数排序、不要打分、不要说"匹配度"
- 不要拿枚举白名单排除人
- 不要拿推导量排除人
- 不要把"未知"当成"不满足"（这两件事混了，等于凭空判一批人不合格）
- 不要为了凑一个好看的名单去放宽或收紧阈值

## 待核 ≠ 不合格(2026-11-21 修正,这条最容易被违反)

**读不到不等于不满足。** 这句话此前只在口头上,代码里有两处反着做,已改:

| 原来的错 | 后果 | 现在 |
|---|---|---|
| `judge_component` 没抽到组件 → 判「不满足」 | 全库 1207 格组件类不满足里 **1192 格(99%)** 是"一项都没抽到" | 记「未知」,进待核 |
| `cv_quality` 读不到品质动作 → 判「无」→ 排除 | 270 人里 235 人被判「无」,第 3 步用它挡掉 165 人 | 判「待核」→ **保留**,进待核清单 |
| `months` 读不出时存 `0` | `>= 24` 静默地对 0 比较 | 存 `None`,不许填 0 |

**改完之后短名单从 4 人变成 164 人** —— 不是标准松了,是原来那 160 个人被一道
读不出来的信号挡掉了。这个数字要如实汇报,不要解释成"我们放宽了"。

### 三条硬规矩

1. `excluded` 里只允许放**硬证据**:属性有值且确实超阈值(年龄 45 vs 25~40)、
   或者职责命中了品质动作但**时长已知**又不足门槛。其余一律 `needs_verification`。
2. 待核的人**留在 kept 里**,同时进 `quality_gate.needs_verification`,带 `why` 与 `quote`。
3. 待核项必须交给能答的人:

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.open_questions --jd <JD>
```

产出 `work/talent/open_questions/<JD>.yaml|.md`,按 **HR / 业务 / 客户** 分组,
每条给"可以照读的问法"与"答完解锁哪一条"。第 4a 步从这里取题,不要自己发明问法。

> 待核清单是**工作队列**,不是免责声明。它存在的意义是让"我们不知道"变成
> "谁在什么时候去问"。没人在问的待核,等于还是把不知道当成了不知道 —— 那就别用它筛选。

## 能力类要求:没读到 = 未知,不是不满足(2026-11-21)

`requirement_library.yaml` 每条要求带 `data_class`,先看它是哪一类:

| 类别 | 没有数据时 | 能不能拿它淘汰人 |
|---|---|---|
| `fact` 事实(年龄/学历/专业/年限) | 未知 | ✅ 有值且不达标才可以 |
| `capability` 能力(英语/品质分析/工具/线束/验厂) | **未知** | ❌ 只有"读到证据且不达标"才行 |
| `soft` 软素质(沟通协调) | **不可判** | ❌ 永远不能 |

实测教训:代码曾把"简历里没读到"判成「不满足」,150 人里 **148 个**没写"品质问题分析"
被判不合格。现在 `judge_component` 没读到一律「未知」,并把该格推进待核清单
(采集方式:业务实测 —— 这类**问不出来**)。

**所以第 3 步真正能排除人的,只有客户原文的事实类门槛。** 能力类全部进待核,靠第 4 步去测。

## 目标人数是**用户输入**,不是脚本常数(2026-11-21)

用户说"我要 10 个""这次 30 个"时,**先写进 jd_inputs,再出名单**:

```bash
python -m scripts.talent.set_target --jd <JD> --interview 30 --shortlist 8~12   # 设
python -m scripts.talent.set_target --jd <JD> --show                            # 看
python -m scripts.talent.pick_interview_list --jd <JD>                          # 按设定出名单
```

两个目标别混:

| 参数 | 含义 | 谁受影响 |
|---|---|---|
| `--interview N` | 第 3 步:从初筛池里挑 **N 个人去面** | HR 的电话产能 |
| `--shortlist M~K` | 第 5 步:面完之后短名单留 **M~K 人** | 交给第 6 步选 ≤4 |

**校验规则(不满足直接报错,不许偷偷改):**
`1 ≤ shortlist_min ≤ shortlist_max ≤ interview_target ≤ 初筛池人数`。
面试批次 < 短名单上限 = 面完还不够挑,必须拒绝并说明。

`set_target` 会把 `decided_by` / `decided_at` / `why` 一起写进 `jd_inputs/<JD>.yaml`,
所以半年后有人问"为什么面 30 个",答案在文件里。

## 切的顺序:九层阶梯,**唯一权威在 `work/talent/OVERVIEW.md` 的「排序口径」一节**

一句话:**越靠前越硬,哈希永远在最后。** 上一层分不出胜负才看下一层。

```
① 硬证据项数(可验证载体:系统/报告/客户审核/图表)   ← 按能力去重,不按要求行
② 软证据项数(只能靠陈述)
③ 用户选的业务优先条件          ← 用户唯一能控的一层
④ 客户原文写的「…优先」条款      ← 客户授权,不是我们的偏好
⑤ 总年限(读不出来排最后 —— 排序口径,不是"不合格")
⑥ 稳定性(平均在职年限,从工作段算出)
⑦ 待核项数(成本,不是优劣)
⑧ 品质岗经历(JD 不要求时这一层关闭)
⑨ sha256(候选人 id)             ← 确定性兜底,不按姓名/文件名
```

**产物里必须带 `cut` 段**,写清切线在第几位、并列几人:

```yaml
cut: {position: 10, tie_band: 2, hash_decided: true,
      note: 切线落在 2 人并列区内,谁上都行(按哈希排)}
```

| tie_band | 汇报怎么说 |
|---|---|
| 1 | 名次可读,可以说"他排第 N" |
| 2~3 | "这几个人键相同,谁上都行" |
| >3 | "**名次不可读**;集合有意义,顺序没有" |

**不许在 tie_band > 1 时说"他更合适"** —— 那是把哈希说成判断。
设计理由、已知偏差、验证方法都在 `work/talent/OVERVIEW.md` 的「排序口径」一节,别在技能里抄第二份。

## 让用户挑优先条件(agent 的标准动作)

用户不需要懂 `skill_线束行业知识` 这种 id。**先列给他看,再按他说的选。**

```bash
# ① 列可选条件(带"池内命中多少人",让用户看到选择的后果)
python -m scripts.talent.priorities --jd <JD> --list

# ② 用户说"第 2 和第 5 条"或"线束 + 验厂" → 按序号或 id 都行
python -m scripts.talent.priorities --jd <JD> --select 2 5
python -m scripts.talent.priorities --jd <JD> --select P-IND-HARNESS P-CUST-AUDIT

# ③ 重排面试名单(不跑这步不生效)
python -m scripts.talent.pick_interview_list --jd <JD>

# 查 / 清
python -m scripts.talent.priorities --jd <JD> --show
python -m scripts.talent.priorities --jd <JD> --clear
```

**汇报时必须带上命中人数**。例:
「线束/连接器行业 20 人 · 客户验厂 5 人 · 品质岗经历有硬证据只有 3 人(选中后名单会很短)」——
用户是在拿"名单长度"换"契合度",不报数他没法选。

**这些条件只影响排队,不影响判定**:
- 不是硬过滤 —— 没命中的人仍在池里,只是排在后面
- 不参与淘汰 —— 第 3 步能排除人的只有客户原文的事实类门槛
- 命中判定**只用简历里真有的证据**,不看 `cv_mock` 模拟填充
- 目录里有 `caveat` 的条件(如按年龄收紧、按词表命中的行业),要**主动把 caveat 念出来**

目录在 `work/talent/priority_catalog.yaml`,可以加条目;不确定命中多少人时先 `--list` 看数。

## 三条禁令(agent 385 在 2026-11-22 的对话里踩了两条)

1. **不许重跑生成器。** `derive_quality_facts` / `screen_cv` 会**重写** `cv_quality.json` 与
   `shortlist/<JD>.yaml` —— 那是"生成"不是"交付"。这一步只许跑三样:
   `set_target` / `priorities` / `pick_interview_list`。
   要看数据就 `read` 已有产物,不要为了"确认一下"就重跑生成器(会把别人刚跑完的结论冲掉)。
2. **交付物必须落在仓库路径**,不是自己的工作区。面试名单在
   `work/talent/shortlist/<JD>.面试名单.md|yaml`;写进 `generated/` 的文件**不叫交付**,
   侧栏和后续步骤都看不到。
3. **先问 JD,再动手。** 仓库里有 10 份 JD。用户只说"面试 30 人"时,不要自己挑一份;
   问一句"哪份 JD"。挑错了后面全部白做。

`quality_gate.failed` 里,没进 `excluded`,第三方复算就对不上账。现在 `screen_cv`
把这一类补进 `excluded`(带 `stage: 品质门槛` 与理由),并单独记
`count.dropped_by_quality_gate`;门禁 `kept + excluded = pool` 不成立就红。
