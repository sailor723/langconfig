你负责**选出最多 4 个人**，并把理由说清楚。产物是 `work/talent/picks/<JD> 选人.md`。

## 第 0 步——先跑判定，再跑选人

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.evaluate --jd <JD> --facts llm --interview --top 0
env -u PGPORT .venv/bin/python -m scripts.talent.pick_final --jd <JD>
```

判定是四态：**满足 / 不满足 / 未知 / 不可判**。这四个状态不许合并：

- **未知** = 简历/面试没读到 → 不是不合格
- **不可判** = 这条要求没有可判的数据项，或 JD 侧没给阈值 → 对所有人都一样，**不算进满足率**

把「未知」折成「不满足」，等于凭空判一批人不合格。这是这套系统最容易犯的错。

## 第 1 步——排序规则（不要自己发明）

```
满足条数多的在前
→ 并列时：未知少的在前（信息完整的人先，不是简历写得多的人）
→ 再并列：不满足少的在前
→ 全并列：按 id（稳定，重跑不换人）
```

**不要用分数排序。** 实测 299 个合格人里 222 人（74%）同分并列，
纯按分数排，"凭什么排第 7"就答不出来。四态计数至少能让每个人说清"满足哪几条、缺哪几条"。

## 第 2 步——最重要的判断：现在够不够格挑

先看这三个数（`pick_final` 会直接给你）：

```
短名单 N 人 · 其中做过一面 M 人 · 可判要求 K/L 条
```

**如果 M 明显小于 4，就直接说现在挑不出来。**

理由要讲明白：没做过一面的人，大量要求是「未知」。这时候按"未知少的优先"排，
排出来的是**谁的简历写得细**，不是谁更合适。缺的不是算法，是第 4a 步的一面数据。

硬凑 4 个名字是最坏的结果 —— 业务领导会以为这 4 个是比过之后选出来的。

## 第 3 步——给每个人一句理由，指向具体条款

不是"综合表现好"，而是：

```
满足 7 条（学历/年限/线束/英语…），不满足 3 条（QC工具/客户验厂/品质分析），未知 2 条（到岗/通勤）
—— 差的三条都在同一族，如果这一族对这个岗不是核心，他值得先面。
```

理由必须能回指到具体的 JD 条款号。说不出来源的理由，等于没有理由。

## 第 4 步——报规则的副作用

"未知少的优先"有一个已知副作用：一个「7 满足 / 1 未知 / 5 不满足」的人，
会排在「7 满足 / 3 未知 / 0 不满足」的人前面。

`pick_final` 会自己列出这种倒置。**照实转述，不要藏**，并给出两种改法让人选：
① 不满足先于未知 ② 先按不满足分档、再按未知分档。

## 交付前回检（**不许跳**）

写结论之前,把**打算写进报告**的每个数字现场重算一遍,并把命令贴出来。

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.evaluate --jd <JD> --facts llm --interview --top 0
env -u PGPORT .venv/bin/python -m scripts.talent.pick_final --jd <JD>
```
**短名单/有一面数据/可判要求 三个数必须是脚本打出来的**;
"挑不出来"这句话也要有脚本依据(有过一面数据的人数 < 4)。

### 为什么必须跑

我交过一份报告,里面真话和假话同时存在:
门禁 161 checks 全绿(真)、HermiT 影响面 114→108→99(真),
但「`_source` 7 行」(实际 48)、「有一行含『主导内审』」(这份 JD 没有)、
「excluded 是抬头标题」(实际是 IATF16949)—— **三句假话**。

它们有同一个来源:**从记忆里写**,而记忆来自另一份 JD 或上一轮。
所以规矩是:**每个数字现场重算,每句"原文有 X"现场 grep。记忆不算证据。**

### 三条自查

1. 这个数字我是刚跑出来的,还是记得的?—— 记得的一律重跑
2. 这句话我能指出在文件的哪个位置吗?—— 指不出就是没读
3. 我是不是把**别处**的内容混进来了?—— 报告里的每一句,都要能在**这一份**产物里找到

### 两条"看着像绿的红"

- **门禁没有汇总行 = 没跑完,不算通过。** 一处 YAML 写坏会让门禁中断,
  而它前面的 PASS 已经打印了 —— `tail` 看着完全正常。只认 `N checks · M failed` 那一行。
- **写完不等于写对。** `write_file` 成功之后必须重跑校验,不能凭"它没报错"。

## 交付时说什么

- 短名单 / 有一面数据 / 可判要求 三个数
- 入选的几个人，每人一句理由（带条款号）
- **如果不够格挑，直说**，并说明缺的是哪一步的数据
- 排序倒置有几处（如果有）

## 绝对不要做

- 不要把「未知」折成「不满足」
- 不要用分数或匹配度排序
- 不要在数据不够的时候硬凑 4 个人
- 不要让 LLM 参与排序或判定（排序必须是确定性的；你只能解释，不能计算）
- 不要写"综合表现优秀"这种没有条款指向的理由
