# 第 4 步 · 一面(采集 + 评语)

> 2026-11-21 起 **4a(采集数据)与 4b(整体评语)合并为一步**:同一通电话只打一次,
> 采集与评语在同一个落盘文件里(`cv_interview/<名>.yaml` 的 `answers` + `review`)。
> 分成两步的代价是同一个候选人被打两次电话,而且评语写的时候采集结果已经凉了。

## 这一步的两个产品(一次访谈,两份产物)

| 产物 | 落在哪 | 谁消费 |
|---|---|---|
| **采集记录**:JD 要的每个数据项,补上值 + 逐字原话 | `cv_interview/<名>.yaml` → `answers` | 第 5 步的四态判定 |
| **整体评语**:他这个人怎么样(不进计算) | `cv_interview/<名>.yaml` → `review` | 业务领导面之前预览 |

**顺序是:先采集,再评语。** 采集是本步的主产品 —— 第 5 步要的数据 8 成靠这一步补。

## 第 0 步——先拿「这个人缺什么」(来自第 3 步的待核清单)

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.open_questions --jd <JD>
```

`work/talent/open_questions/<JD>.md` 按 **HR / 业务 / 客户** 分了组,每项带
「可以照读的问法」和「答完解锁哪一条要求」。**这一通电话要问的就是这份清单**,
不要自己发明问法,也不要问已经不缺的项。

> 第 3 步为什么给不出短名单?因为库里 10 条要求有 5 条数据供给不到 20%
> (品质问题分析 4/270、客户验厂 10/270、品质工具 17/270)。**这些缺口就是本步的工作量。**
> 补完写回 `cv_interview/` 与 `cv_facts.json`,重跑第 3 步,供给率才会上去。


## 三类数据,三种采法(这条决定这一步能不能做成)

问一句「所有数据都由 HR 一面收集吗」——**事实与经历是,能力不是。**

| 类型 | 条款 | 怎么采 | 谁采 | 谁判 |
|---|---|---|---|---|
| **证件** | C-01 年龄 · C-02 学历 · C-03 专业 | 拿材料核(身份证 / 毕业证 + 学信网 / 证书上的专业全称) | HR | 机器比阈值 |
| **面谈** | C-05 年限 · C-06 线束行业 · C-09 客户验厂 · 品质岗经历 | 问经历:哪一段、什么产品、什么体系、他负责哪部分 | HR 采,业务复核 | 机器(年限)/ 业务(行业与验厂) |
| **实测** | C-04 英语 · C-07 品质问题分析 · C-08 品质工具 | **现场做**:给真实不良让他分析、现场画鱼骨图/柏拉图、给一组数据算 CPK、限时写一段英文 8D | **业务**(HR 可发作业) | 业务 |
| — | C-10 沟通协调 | **没有数据项,什么方法都采不出来** | — | 需第 2 步定方法或删除 |

**“问不出能力”是这一步最容易犯的错。** 问「你懂不懂 SPC」「你会不会做品质分析」,
回答永远是"懂、会"。这种"会"一旦记进系统就是**满足**,比「未知」更糟 —— 未知至少诚实。
所以:

- 证件类:**邀约阶段就要**,别占面试时间。
- 面谈类:可以问,但要问"哪一段、哪家客户、你负责哪部分",不接受形容词。
- 实测类:**要么现场做、要么给作业**;答案必须带"他做了什么/给出了什么"的事实,
  而不是"他说他会"。落盘时 `basis` 写 `interview`,引文写他的答案原文,
  **不要把你据此得出的印象写进值里**。

具体每个数据项的采法与问法在 `work/talent/open_questions/<JD>.md` 的「方式」列,
照那张表做,不要自己发明。

## 第 1 步——先出这位候选人的档案,再打电话

一面之前,先把这个人的材料渲染成一份**富化后的 CV 定稿**:

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -m scripts.talent.render_cv_final --id <候选人 id>
# 产物:work/talent/cv_docs/<名>.定稿.md
```

要给整份短名单都出,按 `shortlist/<JD>.目标名单.yaml` 的 `selected` 逐个跑。

### 这份档案有 10 段,你要读的是后四段

| 段 | 内容 | 为什么一面要用 |
|---|---|---|
| C1–C6 字段表 | 31 个字段,每个标 来源 / 逐字引文 / 两侧可比性 | 看清哪些是简历写的、哪些读不到 |
| 工作经历(逐段) | 公司 / 职位 / 起止 / 职责原文照抄 | 电话里对着段问,不要泛问 |
| **品质岗经历** | A/B 档判定 + 硬/弱动作 + 命中段引文 | 判断他到底做没做过这个岗 |
| **稳定性相关** | 任职段数 / 近5年段数 / 平均在职 / 到岗时间 | 全是**推出来的量**(computed),别当原文念 |
| 已识别能力项 | 每项带原文引文 | 问「这条写在简历上,具体怎么做的」 |
| **待补清单** | 31 个字段里读不到的那 20–30 个 | **这就是你的问题清单** |

### 三条纪律

- **派生的量不是原文**。`平均在职年数 3.6` 是从各段起止累加出来的,`到岗时间 4 周` 只有简历真写了才有。
  电话里要问原始事实("上一份做到几月"),不要念推导值。
- **读不到就标〔待补〕**,不要替候选人补。档案里空着的字段,正是一面要填的。
- **品质岗经历有假阳性风险**:判据只看工作段的岗位名与职责,而简历是 OCR 出来的。
  面试时要**复核命中段**:「简历写你在××做检验标准,能说说当时具体做什么吗」。

## 模拟访谈 —— 允许用,但**每份 JD 要单独授权**

没面过但要一份完整档案时(开发、演练、给业务领导看格式),用:

```bash
env -u PGPORT .venv/bin/python -m scripts.talent.simulate_interviews --jd <JD>
```

它写 `cv_interview/<名>.yaml` 的 `answers`,每条 `basis: simulated`。

**能不能被判定/选人采信,不由谁记得,由规则文件说了算:**

```yaml
# work/talent/interview_policy.yaml
default_mode: real_only          # 全局默认:只认真人答案
jobs:
  <JD>:
    mode: mock_allowed           # 这份 JD 允许模拟答案进判定
    decided_by: <谁批的>
    decided_at: <哪天>
    reason: <为什么>
```

- 规则文件里**没有这份 JD** = `real_only` = 模拟答案不进判定。想放开,先在文件里
  写清楚谁批的、为什么,再去跑 —— 不要用 `--include-simulated` 绕过记录。
- 放开之后产物仍必须处处标注(见下),`pick_final` 与 `evaluate` 都读同一份规则,
  不存在两边判定不同的问题。
- 门禁 `check_component_catalog` 会复查:产物里的规则段、每行数据来源、
  模拟行是否真只有模拟答案、md 里的演练横幅。**少一处就是红。**

### 四条硬约束

| # | 约束 | 为什么 |
|---|---|---|
| 1 | 每条答案必须 `basis: simulated` | 渲染器据此把来源写成 **`代拟(模拟)`**,而不是 `interview` |
| 2 | CV 定稿顶部必须出现「本档案有 N 个字段来自模拟访谈」横幅 | 有人会把档案转手,横幅是最后一道防线 |
| 3 | **个人身份字段不许编**:姓名 / 电话 / 邮箱 / 婚姻 / 籍贯 | 编了会被当真实档案使用;而且它们对「能不能干这个岗」没有判断价值 → 保持〔待补〕 |
| 4 | **真访谈永不被覆盖**:文件里有 `basis: interview` 的答案就跳过 | 实测踩过:一次 `--overwrite` 把 21 问 22 答的真访谈评语盖掉,只能从 git 捞回来 |

### 怎么一眼分出真假

```
真访谈:  > 来源:电话初筛 · 2026-11-20 · 面试人 (我方)     字段来源列 = interview
模拟:    ⚠ 本档案有 10 个字段来自「模拟访谈」             字段来源列 = 代拟(模拟)
```

**对外之前必须换成真实访谈记录** —— 换的时候只改 `answers`,把 `basis` 改成 `interview`
并把值改成真人说的原话,不要只删标记。

## 第 3 步——问法

- 沿着 JD 原话问，但**不要把 JD 念给候选人听**（那是让他背答案）
- 要听具体的事，不是"会不会"：「用过没有、上一次用是什么时候、你在其中负责哪一段」
- 每得到一个回答，立刻想清楚它落成什么：一个数？一个属性？一个组件？

## 第 4 步——落盘：三种落法，必须显式写

```yaml
answers:
  - field: F.EDU_LEVEL            # 落进哪个档案字段
    props: {education_rank: 3}    # 直接定值（属性）
    question: 三段学历分别是什么层次？
    answer: 广东司法学校中专；东莞职业技术学院大专；暨南大学自考本科
    note: 简历只写了校名，没写层次

  - field: F.EXP_ACTIVITY
    establishes: [skill_客户验厂]   # 这条回答坐实了哪个组件
    question: 「熟练应对二方与三方审核」是客户来厂审，还是你审供应商？
    answer: 客户来我们厂是主要的，日系每年一次，从首次会议到整改关闭都是我接待
    note: 简历那句话读不出角色，只有问才知道
```

**`establishes` 必须由你（采访人）写，不许程序推测。**
原因是「熟练应对二方与三方审核」这句话读不出"被审还是审人"——
映射到哪个组件是一个采访判断，不是文本相似度能算的。

## 第 5 步——三条硬规矩

1. **来源要分开**：简历原文是 `resume`，这场对话是 `interview`。
   混成一个来源，出了问题查不出是哪一环 —— 简历错了是简历的事，访谈错了是我们记录的事。
2. **不许把候选人说的话写成简历原文**。他没写在简历上的，来源就是 interview。
3. **没有刻度的东西不要安刻度**。「口语一般」就记「口语一般」，不要换成「B1」。
   换成等级只是让它看起来可算，实际上是假精度。

## 第 6 步——收尾：报缺口，分责任

问完再跑一次第 0 步的命令，报：

- 这个岗 N 条要求里，现在**够了几条、还缺几条**
- 每条缺口**是谁的责任**：
  - 候选人没说清 → 下一轮补问
  - 客户没给阈值（比如薪资预算、上班地点还没定）→ 找客户，问候选人没用
  - 模型没有可判的数据项（E 维素质类）→ 这类永远判不了，只能进"人看的部分"

最后一种要说清楚：**这类要求不是"没问到"，是"问了也算不出来"**。

# 第二部分 · 整体评语(同一通电话的第二份产物)

## 第一原则：能变成要求，就不要变成评语

HR 说「我觉得他不太稳定」时，先问一句：**这个担心能不能落成一条可判定的要求？**

- 能 → 「近 5 年任职公司不超过 3 家」是一条要求，有阈值、能算、能回查。**退回 4a 去问，或者建议新增一条 HR 要求（带 rationale）。**
- 不能 → 「我觉得他态度一般」落不成要求，因为它没有数据项。这种才写进评语。

为什么必须这样分：评语没有刻度、没有出处、换个人写结论就变。
「沟通表达 4 分」说不清 4 分是谁定的。而要求即使判不了，也会诚实地落成「不可判」——
不需要另外发明一个刻度。

**所以：评语里不许出现分数、等级、星级、百分比。** 一出现，就是在把主观印象伪装成计算。

## 第 7 步——先看这场访谈是真的还是模拟的

打开 `cv_interview/<名>.yaml`,看 `answers[].basis`:

```
basis: interview  → 真访谈,正常写评语
basis: simulated  → **模拟答案(开发/演练用)**,评语里必须写明:
                    「本评语的依据是模拟答案,不是真人说的」,并且这份评语不得进任何对外材料
```

拿模拟答案写出一份"像模像样"的评语,最危险 —— 它长得和真评语一模一样,
下一个人分不出来,于是"我方假设"就变成了"面过的印象"。

## 第 8 步——写三行，按这个结构

```yaml
review:
  heard: "他主动说上一家是主动离职，因为厂区要搬。问到时没回避，细节对得上。"
  basis: "工作经历 6 段、近 5 年 3 段、平均 3.6 年 —— 数据上不算频繁跳槽；离职原因问得具体，能复述。"
  reservation: "口语自评『一般』，没有客观刻度，只能按原话记；日系客户主要靠翻译，这一条我保留意见。"
```

- `heard`：我听到了什么（可复述的事实，不是判断）
- `basis`：我据此怎么判断，**带上数据或原话**
- `reservation`：我的保留意见 / 不确定的地方

三段都要有。只有 `heard` 没有 `basis`，读者没法判断你的判断靠不靠谱；
只有 `basis` 没有 `reservation`，等于声称自己全看透了。

## 第 9 步——哪些话不许写

- 「综合素质好 / 一般 / 较差」—— 没有依据的形容词
- 「感觉不太稳定」—— 如果真有依据，那就该是一条要求（见第一原则）
- 「建议重点考虑 / 不推荐」—— 这是决定，不是评语。决定由第 5 步和业务领导做
- 任何分数、等级、排名

## 第 10 步——明确写出"这份评语不进计算"

在 yaml 里写清：

```yaml
review:
  joins: false        # 明确：不参与 join，只随档案给业务领导看
  known_gaps:         # 这些是"问了也算不出来"的，不是没问到
    - "沟通协调能力：E 维无组件，判不了"
```

## 交付前回检（**不许跳**）

写结论之前,把**打算写进报告**的每个数字现场重算一遍,并把命令贴出来。

```bash
cd <repo>/backend && set -a && source ../.env; set +a
env -u PGPORT .venv/bin/python -c "
import yaml
d=yaml.safe_load(open('../work/talent/cv_interview/<候选人>.yaml',encoding='utf-8'))['review']
for k in ('heard','basis','reservation'): print(k, '=>', bool(d.get(k)))
print('joins =', d.get('joins'))"
```
三段都要在;`joins` 必须是 false;**全文不许出现分数、等级、百分比**(出现了就不是评语,是打分)。

### 为什么必须跑

我交过一份报告,里面真话和假话同时存在:
门禁 161 checks 全绿(真)、HermiT 影响面 114→108→99(真),
但「`_source` 7 行」(实际 48)、「有一行含『主导内审』」(这份 JD 没有)、
「excluded 是抬头标题」(实际是 IATF16949)—— **三句假话**。

它们有同一个来源:**从记忆里写**,而记忆来自另一份 JD 或上一轮。
所以规矩是:**每个数字现场重算,每句"原文有 X"现场 grep。记忆不算证据。**

### 三条自查

1. 这个数字我是刚跑出来的,还是记得的?—— 记得的一律重跑
2. 这句话我能指出在文件的哪个位置吗?—— 指不出就是没读
3. 我是不是把**别处**的内容混进来了?—— 报告里的每一句,都要能在**这一份**产物里找到

### 两条"看着像绿的红"

- **门禁没有汇总行 = 没跑完,不算通过。** 一处 YAML 写坏会让门禁中断,
  而它前面的 PASS 已经打印了 —— `tail` 看着完全正常。只认 `N checks · M failed` 那一行。
- **写完不等于写对。** `write_file` 成功之后必须重跑校验,不能凭"它没报错"。

## 交付时说什么

- 这份评语**不进计算**，只是材料
- 有哪几条担心被你**退回**变成了要求（这是本技能的产出之一，往往比评语本身有用）
- 有哪些要求是"问了也算不出来"的，为什么

## 绝对不要做

- 不要写分数、等级、星级
- 不要下"推荐 / 不推荐"的结论（那是第 5 步的活）
- 不要把能落成要求的担心留在评语里（那等于放弃了让它被检验的机会）
- 不要只写 `heard` 不写 `basis`
- 不要问已经不缺的项（浪费面试时间，也让候选人以为我们在走过场）
- 不要把回答写成一段自由文字（问完落不进字段，等于没问）
- 不要自己推测 `establishes` 的映射
- 不要给主观判断安一个数字（那是 4b 的事，而且不进计算）
- 不要漏掉"答案格式"那一栏：每条答案都要能写进同一个字段，否则问了也用不上
