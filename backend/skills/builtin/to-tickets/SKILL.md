## Instructions（指令）
单位是**曳光弹**：一条穿过每一层、窄但**完整**的路径，能单独演示，小到可以放进一个全新的上下文窗口。
工单不是一份步骤清单——它们是一张**任务图**，而有用的输出是**前沿**：现在就可以开工的那些工单。

### 第 0 步——没有父文档就拒绝切工单

读 `spec_path`。没有已同意的规格 → 停下：*"没有已同意的规格；先跑 to-spec"*。切工单过程中才发明出验收标准的工单，
是没人能验证的工单。

### 第 1 步——先探索再切片

读规格会触及的代码。寻找能**让之后每张工单都更小**的**预重构**（"先把改动变容易，再去做容易的改动"）：一个接缝、
一个被抽出来的函数、一个缺失的测试装置。预重构单独占一张工单，排在最前，其余工单全部被它阻塞。

### 第 2 步——纵向切，并写清阻塞

对每一片：

- 它在 schema → service → API → UI → 测试 这些层里**穿过去**（存在哪层就穿哪层），而不是只填一层；
- 它**能单独演示或验证**——规格里的 4 条标准满足 4 条，不是"每条做一半"；
- 它放得进一个全新的上下文窗口；放不进就拆，不要拉长。

给每张工单写清它的**阻塞边**——必须先落地的工单。没有阻塞的工单就在前沿上，可以立刻开始。

**宽重构是例外。** 一次机械改动（重命名、类型变更）如果爆炸半径覆盖整个代码库，它不可能是一个曳光弹——
中途没有任何东西是绿的。把它排成 **expand → 分批 migrate → contract**：

1. *expand*：把新形态加在旧形态旁边，什么都不破；
2. *migrate*：每批一张工单（每个包、每个目录），各自被 expand 阻塞；
3. *contract*：删掉旧形态，被所有 migrate 批次阻塞。

如果连批次都无法单独保持绿，保留这个序列，但让它们共享一条集成分支，并全部阻塞一张最终的"集成并验证"工单——
**只在那一张工单上承诺绿。**

### 第 3 步——一张工单一个文件

`params.ticket_dir/NNN-<slug>.md`，三位数编号，按**依赖顺序**编（不必是执行顺序）：

```
# 003 —— <标题>

Spec: docs/specs/<slug>.md#AC2, AC3      Blocked by: 001, 002      Size: S | M | L（一个上下文窗口）

## 交付
这张工单让什么端到端行为变真，一段话，用用户的语言。如果你非要列举"层"才能写出这段话，这个切片就是横向的——重切。

## 验收（验证者会检查什么）
- [ ] <可检查的标准，抄自或收窄自规格的 AC 表>
- [ ] <以及将要证明它的测试/命令>

## 不在这张工单里
它有意留给后面工单的东西，避免两个智能体都去做。

## 备注
探索时发现的接缝，以及任何会改变切法的东西。
```

规则：

- **每张工单至少有一条可检查的验收行。** 如果你能写的最好的一句是"能正常工作"，这张工单就没准备好——那正是
  `to-validation` 存在的理由。
- **验收行要能回溯到规格的 AC 编号。** 一张工单不满足规格中任何一条标准，就是范围蔓延；要么它属于规格，
  要么它是一份新规格。
- **阻塞要用工单号写**，不要写成散文。"在 API 之后"不是一条边。
- **一张工单只为一个理由存在。** 两个理由 → 两张工单。
- 不要在工单上写小时数预估。这里唯一有意义的尺寸是"放得进一个上下文窗口"。

### 第 4 步——过一遍，然后停下

把这张图摆成一份清单——`NNN 标题 · 被 … 阻塞 · 交付 …`——并附上当前的**前沿**（没有阻塞的那些），然后问：
*"这样切符合你想要的吗，前沿是你预期的吗？"* 在任何人开工之前，把他们反对的地方改掉。**不要在这个技能里
开始实现。**

### 什么时候不要用

- 只有一张工单的工作量：写完直接做。
- 没有已同意的规格：先跑 `to-spec`（它背后是 `Grilling`）。
- 这个"计划"其实是一次调查：用 `research` 或 `diagnosing-bugs`，它们产出发现，不是工单。
