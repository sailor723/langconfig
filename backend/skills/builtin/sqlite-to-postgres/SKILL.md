你的任务：**把一个 SQLite 文件变成一个人和 SQL 都能核对、agent 能反复查的 PostgreSQL 库**。
交付物是「迁移 + 一份核对结论」，不是「我把表建出来了」。

**先记住一条**：SQLite 文件里已经写着类型（`REAL`、`TEXT`、`INTEGER PRIMARY KEY AUTOINCREMENT`），
所以这里的活是**忠实翻译 + 证明**，不是推断。推断错误在这里是静默的：一个挪了 0.01 的金额照样能渲染出看板。

## 第 0 步——先量源库，不要先动手

**动手之前先读 [references/rules.md](references/rules.md)**（七条编号规则，每条都写了「跳过会怎样」；三条挂在本技能的迁移脚本上，四条老实标成 advisory）。


```
sqlite3 <file>.db ".tables"                                  # 有哪些表
sqlite3 <file>.db "select count(*) from <t>;"                 # 每张表多少行
sqlite3 <file>.db ".schema"                                   # 声明类型、主键、AUTOINCREMENT
```

要拿到的是四件事：**表清单、行数、主键（单列？复合？TEXT？）、每个数值列的声明类型**。
这四件事决定了类型对照表，而类型对照表是下一步要给人看的东西。**不要凭列名猜类型**——
一个叫 `amount` 的列在 SQLite 里完全可能是 `TEXT`。

## 第 1 步——出类型对照表，先给人看

用仓库里的 `backend/scripts/migrate_sqlite_to_postgres.py` 做迁移，它实现的对照是：

| SQLite 声明 | PostgreSQL | 为什么 |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | 自增要保留，否则新插入没有 id |
| `INTEGER PRIMARY KEY` | `bigint PRIMARY KEY` | 值本身就是身份（如 `company.id`） |
| `TEXT PRIMARY KEY` | `text PRIMARY KEY` | `period`='2026-11'、`kpi_id`、`phase_id` |
| `REAL` / `FLOAT` / `NUMERIC` | **`numeric`** | 存成 float 会漂：`0.9459` 必须还是 `0.9459` |
| `INTEGER` / `BOOLEAN` | `bigint` / `boolean` | 0/1 标记列 |
| `TEXT` / `DATE` / `DATETIME` | `text` | **故意**，见下一节的 `period` |

把这些念给人听，特别是第 4 行和第 6 行——它们各自都有一个"看起来更合理、实际会坏"的替代方案。
用户说"可以"才继续。

## 第 2 步——迁移，并当场证明

```bash
python backend/scripts/migrate_sqlite_to_postgres.py \
    --source /path/to/<file>.db --dbname <目标库> [--recreate]
```

**连接参数不要写在命令行上。** 这个脚本自己读部署的 `.env`（`POSTGRES_HOST/PORT/USER` + `POSTGRES_PASSWORD`），
所以正常情况下一个参数都不用传。**绝不**在命令里写 `export PGPASSWORD=…` 或 `--password …`——
那会把口令留在转写记录、日志和交付报告里，而"迁移脚本能连上"完全不需要它。

它会 `CREATE DATABASE`、按对照表建表、逐表 `execute_values` 灌数，然后**自己核对**：

```
verification
  PASS fact_kpi_monthly         rows 168 vs 168
  …
OK — 23 table(s) migrated into <目标库> and every count and numeric sum agrees.
```

核对是两层：**行数**（少了行）和**每个数值列的 SUM**（行数对、数值变了——这是行数看不见的那类错）。
`--verify-only` 只核对不写，适合"我怀疑有问题"的时候。

**核对不 PASS 就停。** 不要"先跑起来再说"：迁移错一位数，后面每一张报表都跟着错，而且没人会知道。

## 第 3 步——迁移后一定会浮出来的四件事（这一步是重点）

搬过去的只是数据；**可执行的 SQL、维度里的 id、单位、时间语义**都要单独检查，因为它们不随数据一起翻。

### 3.1 存成文本的 SQL：`?` → `%s`

很多这类库里有一个"公式字段"（`dim_kpi.formula`、视图定义、报表模板），里面存着**带占位符的 SQL**。
SQLite 用 `?`，PostgreSQL 用 `%s`。迁移不会翻这个，结果有两种：

- 报错（好，你能看见）；
- 或者**跑通但永远匹配不到**（坏，看不见）。

实测：一个 25 条公式的 KPI 目录，25 条全部只需要把 `?` 换成 `%s` 就能在 PG 上跑通，
而且跑出来的值与迁移后的 `facts` 表逐条一致。**把这一步当成验收标准**：

```bash
# 每条公式在 PG 上跑一遍，并与事实表的值对比
# 这就是"迁移之后算术还一样"的证据，而不是"表都在"
```

### 3.2 维度-事实 join：id 被清洗过

生成数据的脚本常常把文件名/键名清洗过（`/`→`_`、括号→`_`），而**维度表是另一个脚本写的**，
于是同一个业务对象在两张表里是两个字符串：

```
dim:  RS05_海关违规/罚款金额        fact: RS05_海关违规_罚款金额
```

`25/28` 能 join，3 个 join 不上——**而且它们恰好是最严重的三个**（海关罚款、核心骨干流失、订单流失），
在看板上表现为"卡片不见了"，不是报错。所以：

```sql
select distinct kpi_id from fact_kpi_monthly
except select kpi_id from dim_kpi;          -- 立刻把孤儿 id 点名
```

**join 不上就是缺陷，不要让视图用 LEFT JOIN 把它藏成 NULL。**

### 3.3 单位和 scale

`REAL` → `numeric` 只是不让数字漂；**展示口径**（0.9459 还是 94.59%）仍然要声明。
迁移前后都要问一句：这个库里有没有"比率以小数存储、却按百分比展示"的列？
如果有，就在目标库里显式声明（例如本体里的 `:scale "100.0"`、或视图里 `* 100`），
否则同一份数据在卡片上是 `0.9`、在图上是 `94.59`。

### 3.4 `period` 是字符串，未来的行不是"实际值"

- `period` 保持 `text`：图省事改成 `date` 会让所有 `where period = 'YYYY-MM'` 的公式失效。
- **看 row 的日期**：如果库里有超出"今天"的月份却填在 `actual` 列里，那不是实际值，是预测/情景。
  迁移不改这个事实，但**必须说出来**——否则"实际 vs 目标"的读数被未来月份污染。

## 第 4 步——登记成数据源

迁完不要只给一句连接串。注册进 **Settings → Databases**，agent 才能通过「Agent 编辑器 → Database」直接用它：

```bash
python backend/scripts/seeds/in/register_database.py \
    --name <源名> --label "<中文名>" --dbname <目标库> \
    --host 127.0.0.1 --port 5433 --user <user> --password <password>
```

口令以 Fernet 加密存库、接口只返回"已设置"，运行时以 `PGPASSWORD` 进沙箱。
**不要**把连接串（尤其含口令的）写进 prompt、报告或交付物。

## 第 5 步——交付

四样一起给：**目标库与连接方式（不含口令）**、**逐表行数 + 核对结论（PASS）**、
**迁移后检查的四个结论**（占位符 / 孤儿 id / 单位口径 / 未来期间）、**已知缺陷清单**（你查出来但没有改的）。

最后一行永远是：哪些数字现在可以放心用，哪些不行。迁移是忠实翻译，**不是纠错**——
源库里的缺陷会原样搬过来，说清楚比悄悄改掉更有用。

## 拒绝清单（硬契约）

- **不在核对 PASS 之前宣布迁移完成**——行数或数值合计任一不符就停；
- 不把 `REAL` 翻成 `float`（会漂）、不把 `TEXT` 的 `period` 翻成 `date`（会打断字符串匹配）；
- 不因为"表都在、能 select"就说迁移成功——那是最容易被误认成成功的状态；
- 不隐藏孤儿 id（`LEFT JOIN` 成 NULL）、不把比率的小数展示说成百分比；
- 不把超出今天、填在 `actual` 列里的月份说成实际值；
- 不在交付物里写口令或含口令的连接串；**也不在命令行里**（`export PGPASSWORD=…`、`--password …` ——
  脚本自己读部署的 `.env`，没有理由把口令写进转写记录）；
- 不擅自"顺手修复"源库的业务缺陷——除非用户明确要求，且逐条说明改了什么、为什么。

## 与其它技能的接线

- 迁完要查数、写 SQL → `db-query`（三条路径、表名靠查不靠猜）；
- 源数据本来是 Excel/CSV、还没进任何库 → `excel-csv-to-postgres`（那张技能从文件建库，这一步从库搬库）；
- 交付前要自证 → `evidence-first-delivery`（行数、数值合计、孤儿 id 都是要贴出来的证据）。
