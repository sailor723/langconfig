# 迁移的规则

七条。每一条都来自一次真实的迁移（2026-11-11，一个 23 表 / 2 361 行的 SQLite KPI 库搬进 PostgreSQL），
"跳过会怎样"那一行写的是实际发生过的事，不是提醒。

## 1. 先量源库，再动手

`schema` 与每表行数先拿到手：表清单、主键形状、每个数值列的**声明类型**。声明类型是这张库唯一可靠的
类型来源，列名不可靠（叫 `amount` 的列完全可能是 `TEXT`）。

*跳过会怎样：* 先建表后对数据，类型错了要重建一遍，而错的那一列已经在视图和报表里被引用了。

**Gate:** `migrate_sqlite_to_postgres.py` —— 它用 `pragma table_info` 逐列取声明类型并打印对照表；
`--verify-only` 用它自己的 introspect 再量一次目标库

## 2. 类型按声明翻，不按值猜

`INTEGER` → `bigint`，`BOOLEAN` → `boolean`，`REAL/FLOAT/NUMERIC` → `numeric`，`TEXT/DATE/DATETIME` → `text`。
`INTEGER PRIMARY KEY AUTOINCREMENT` 要变成 `GENERATED BY DEFAULT AS IDENTITY`，否则迁完新插入没有 id；
复合主键不要给任何一列加 IDENTITY。

*跳过会怎样：* 自增丢失后第一次写入就撞主键；复合主键被当成 identity 会让插入直接报错。

**Gate:** `migrate_sqlite_to_postgres.py` —— `pg_type()` 与 `ddl_for()`，两者都有单元测试（含复合主键与
自增两条 DDL 断言）

## 3. `REAL` 进 `numeric`，不进 `float`

SQLite 的 `REAL` 是双精度浮点，迁移时如果直接建成 `double precision`，`0.9459` 这类值会在后续运算里漂。
建 `numeric` 可以按写下来的十进制原样保存。

*跳过会怎样：* 金额/比率的合计差一分钱；行数完全对得上，所以没人发现。

**Gate:** `migrate_sqlite_to_postgres.py` —— 迁移后逐表比对**每个数值列的 SUM**，不一致即 `MIGRATION HAS
DIFFERENCES`（变异测试：改一行金额，必须报红）

## 4. `period` 保持字符串

`'2026-11'` 这种月份在库里是**主键与过滤条件**，改成 `date` 会让所有 `where period = 'YYYY-MM'` 失效。
需要类型化的日期另外加列或建视图，不要在迁移里改变一个字符串的含义。

*跳过会怎样：* 迁移后每条公式都返回 NULL —— 因为 `'2026-11' = date '2026-11-01'` 永远是假。

**Gate:** `migrate_sqlite_to_postgres.py` —— `pg_type('TEXT')='text'` 且 `period` 原值逐字节核对（往返测试）

## 5. 存成文本的 SQL 必须重放一遍，`?` → `%s`

这类库里常有一个"公式字段"（`dim_kpi.formula`、视图定义、报表模板）存着带占位符的 SQL。
SQLite 用 `?`，PostgreSQL 用 `%s`。迁移不会翻它，两种结局：报错（看得见），或者**跑通但永远匹配不到**（看不见）。

*跳过会怎样：* 实测一个 25 条公式的 KPI 目录，全部只需要 `?` → `%s`；不翻的话每一条都在"成功执行且返回空"
的状态里，而看板只会显示"—"。

**Ungated (advisory)** —— 目前没有门禁能自动发现"这条 SQL 的占位符方言不对"；验收动作是人工把全部
公式在目标库上跑一遍并与事实表对比（这次是 25/25 一致）

## 6. 维度-事实的 id 要实测，不要假设

生成数据的脚本常常清洗过键名（`/`→`_`、括号→`_`），而维度表可能是另一个脚本、另一套命名。
同一个业务对象于是变成两个字符串，`join` 静默少几行。

*跳过会怎样：* 实测 28 个 KPI 只有 25 个 join 得上，丢掉的三个（海关罚款 / 核心骨干流失 / 订单流失）
在看板上就是"卡片不存在"，没有任何报错。

**Ungated (advisory)** —— 一条 SQL 就能点名：
`select distinct f.<id> from fact f except select <id> from dim`；把它写进交付物的核对清单

## 7. 迁移是忠实翻译，不是纠错

源库里的业务缺陷（会缩小的分母、恒为 0 的比值、被填成默认值的 target、超出今天却写在 `actual` 里的月份）
会原样搬进 PostgreSQL。迁移的职责是**搬对 + 说清楚**；修复是另一件事，要用户点头、且逐条说明。

*跳过会怎样：* 顺手"修好"了几条，结果没人知道迁移前后的数字为什么不同，也就无法判断迁移本身对不对。

**Ungated (advisory)** —— 拒绝清单写在交付物里；改动必须逐条列前值与后值
