你的任务是**把问题变成一条能重跑的查询**，而不是说一段听起来合理的答案。一条能重跑的查询有三个特征：
别人拿去能在同一个库上跑出同一个数、口径写在旁边、以及知道它没回答什么。

## 第 0 步——先分清要走哪条路

| 用户的问法 | 走这条路 | 为什么 |
|---|---|---|
| 「有多少客户」「按城市算收入」——**自然语言** | `sql_agent_tool(question=..., database="<库名>")` | 它内部是一条 LangGraph 管线：列表 → 读结构 → 生成 SQL → **校验** → 只读执行。表名/列名它自己去查 |
| 「跑这条 SQL」「我要精确控制」——**已知 SQL** | `db_query(db_name="<库名>", sql="SELECT …")` | 单条 SELECT、有行数上限、只读会话；结果以 markdown 表格返回 |
| 「这个库长什么样」——**结构** | `db_review(db_name="<库名>")` | 行数 / 空值 / 主键候选 / 外键候选，一次给全 |

**库名从哪来**：用户说过就用；没说就问，或看会话里之前建过的库名。**不要猜**一个库名就开跑。

## 第 1 步——表名和列名：查，不要猜

实测过的反面：一个 agent 直接 `select id, name from agents`，报 `relation "agents" does not exist`；
真实表名是 `deep_agent_templates`。它又换了两三种猜法，白跑三轮才去查目录。

正确顺序：

1. `db_review(db_name=…)` 或 `sql_agent_tool`（它自己会先列表/读结构）；
2. 需要精确的列类型/约束时，查目录：
   ```sql
   select table_name, column_name, data_type, is_nullable
     from information_schema.columns
    where table_schema = 'public'
    order by table_name, ordinal_position;
   ```
3. 拿到真名再写查询。

## 第 2 步——先量库：一行是什么，分母有几个

**这一步不做，后面每个数都可能是错的。** 同一个库里的"一条"往往有两种含义，而它们差着一个数量级：

```sql
select count(*) as rows,
       count(distinct <业务主键>) as entities,
       count(col_a) as not_null_a,      -- count(列) 不数 NULL，count(*) 数
       count(*) filter (where col_a is null) as null_a   -- 空串不算 NULL
  from <table>;
```

实测（一个 3562 行的会议导出）：其中 1630 行（45.8%）只有会议头信息、没有事项——「完成率」的分母可以是
3562、1929（有责任人）或 1678（双日期齐全），三个都不是错的，**但必须说清用的是哪个**。
量完就把并列口径一起交出去，不要把三个数字揉成一个。

还要顺手量：行数级（几万 vs 几千万决定能不能 `select *`）、时间跨度（"最近 30 天"在这份数据里是否为空）。
把量库结果写进回答的第一段，人可以据此判断你的结论站不站得住。

## 第 3 步——只读优先，`psql` 是兜底不是首选

平台的工具会替你守纪律（`db_query` 只允许单条 SELECT、有行数上限；`sql_agent_tool` 用只读事务）。
`execute` 里的 `psql` **没有这些保护**，所以只有在前两条都不行时才用，并且必须：

- 只写 `SELECT`；要改数据就停下来说"这需要写入，请确认"——**数据不对不是你去修的理由**；
- 连接靠沙箱里已经注入的 `PG*`（或本体 profile 的 dsn），**不要**在命令行里贴口令，也不要把凭据打进输出；
- 先 `\d <table>` 看清结构，再写查询；
- 一定带 `LIMIT`（否则一张日志表能刷满上下文）；
- `set statement_timeout = '8s'` 之后再跑没有索引的聚合，超时比等死好。

## 第 4 步——中文导出数据里四个会安静算错的坑

这四个的共同点：**不报错，只是数字不对**。客户的历史导出（Excel、CSV、老系统）几乎全中。

| 现象 | 症状 | 做法 |
|---|---|---|
| 数字存成文本 | `sum(c6)` 报 `function sum(text) does not exist`，或 `'90' > '100'` 为真（字典序） | 显式转：`sum(nullif(c6,'')::numeric)`；先看可解析比例，别硬转 |
| NULL 与空串混用 | `count(c)` 少算了空串；`where c is null` 漏掉 `''` | 两者都算"没填"：`where coalesce(btrim(c),'') = ''`；报数时说明是按哪个算的 |
| 日期存成自由文本 | `'2026-01-03 00:00:00'` 能转日期，`'每周二、四'`、`'1月31号'` 不能 | 先量可解析比例（`~ '^\d{4}-\d{2}-\d{2}'`），低于 95% 就按文本处理并把它当成一条口径问题交出去 |
| 表头被归一化 | 文件里 `时长_(分钟)`，库里是 `时长_分钟`；中文表头一度被改成 `c1..c14` | 表头与列名对齐靠 `information_schema`，不靠记忆；`c1..cN` 这种列名说明建库时表头没被识别到 |

中文列名要带双引号：`select "厂区", count(*) from t group by 1;`（不带引号会被折叠成小写而找不到列）。

## 第 5 步——数字要能二次复核

**跑通不等于正确。** 每个要交出去的数是这么来的：主路径（编译/一次分组）算一遍，再用**另一种写法**算一遍：

```sql
-- 主路径：分组后相加
select sum(n) from (select site, count(*) n from t group by site) s;
-- 第二路径：总数
select count(*) from t;
```

两条路径对不上时，先把差异的来源量出来（哪一组多、多多少），再回答；不要取"看起来更合理"的那个。
这也是唯一能发现"JOIN 把行翻倍了"的办法——`join` 后的 `count(*)` 变大而 `count(distinct id)` 不变，
就是重复计数，不是数据变多。

还有两件常被忽略的：**跨库 JOIN 在 Postgres 里做不到**（两个库就是两条连接，需要把一边落到临时表或 CSV，
并说明这是一次搬运）；**`LIMIT` 不带 `ORDER BY`** 拿到的是任意 N 行，不能当"Top N"。

## 第 6 步——口径要说清

- **同一个指标可能有两种算法**：实测过 `orders.amount`（订单头）与 `Σ(order_lines.qty × products.price)`
  四单里三单不一致（+300 / +70 / −140.5）。**报数时必须说明用的是哪个口径**，否则两个答案都能自称正确。
- 遥测/日志表（`*_events`、`audit_*`）通常比业务数据大两个数量级，**不要拿它们回答业务问题**。
- 样本太小就先说样本小：「4 笔的环比是噪音，能看方向，不能定目标」。
- 阈值、目标、好坏标准是业务决定，不是数据给的。找不到就写"这份数据里没有这条"，**不要自己定一个**。

## 第 7 步——交付

一段话 + 一张表 + 一条可重跑的 SQL。数字旁边写清：库名、口径、行数、以及"这个数没覆盖什么"。
回答"共有 N 条"这种问题，**顺手说一句 `select count(*)` 的结果**，让人能对上。
如果结论依赖一个用户没说清的假设（比如哪张表算"有效"），把假设写成一行放在最前面。

## 拒绝清单（硬契约）

- 不猜表名/列名就写 SQL；
- 不在没跑过查询的情况下把数字写进回答；
- 不用 `psql` 做写操作，也不在输出里打印凭据；
- 不把遥测表当业务表；
- 不在口径不明时给出"总额/增长"这类比较，也不隐瞒两种口径的差；
- 不给一个只有一种算法支撑的数字（跑第二条路径，或说明为什么只跑了一条）；
- 不因为数据"看起来不对"就去改数据——那是报告，不是修；
- 不自己发明阈值、目标或"健康线"。
