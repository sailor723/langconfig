你的任务是**在动任何代码之前，先让这个仓库变得可预测**。输出是一张能被核对的地图，不是一段读后感想。

## 第 0 步——先确认代码在不在这里

```bash
pwd && ls -la | head -20
git -C . rev-parse --show-toplevel 2>/dev/null || echo "not a git repo here"
```

**你的文件工具与 shell 都被限制在一个工作区里**。如果用户点名的是工作区之外的路径，**直接说清楚**：「我只能在
<workspace> 里读写；要改那个仓库，请把它 clone 或复制进来。」不要假装读到过，也不要凭目录名推断内容。

## 第 1 步——先拿骨架，别读文件

按这个顺序花最少的钱拿到最多结构（每一步都贴出你实际跑的命令与输出）：

1. **清单**：`ls` 顶层 + 一层目录树，**不要** `find /` 或全量 `tree`（会超时，也会淹没上下文）。

   ```bash
   find . -maxdepth 2 -type d -not -path '*/node_modules*' -not -path '*/.git*' | head -60
   ```

2. **它是谁**：`README*`、`package.json` / `pyproject.toml` / `Cargo.toml` / `go.mod` 的 `scripts` 与依赖段。
   **构建与测试命令只能从这里读出来，不许靠猜**（`npm test` 还是 `pnpm test`，`pytest` 还是 `uv run pytest`）。
3. **入口在哪**：`main.py` / `app.py` / `src/main.ts` / `index.ts` / `cmd/*` —— 从清单里挑，不要搜全库。
4. **测试在哪、怎么跑**：`tests/`、`__tests__`、`*.test.*`、CI 配置（`.github/workflows/*`）。**CI 里那行命令才是
   这个仓库的真实答案**，README 常年过期。
5. **它自己的规矩**：`AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` / `docs/` / lint 配置（`ruff`、`eslint`、
   `tsconfig` 的严格度）。仓库自己的规矩优先于任何"通用最佳实践"。

**六个锚点够了。** 不要为了"彻底了解"去读几十个文件——你会在上下文里迷路，而地图仍然不准。

## 第 2 步——把地图写成表，每条都能核对

```
它是什么        | 在哪里                        | 证据
HTTP 入口       | src/api/app.ts                | `grep -n "createServer" src/api/app.ts` → 12:createServer(
数据访问        | src/db/*.ts                   | `ls src/db` → client.ts index.ts queries.ts
测试怎么跑      | package.json + .github/workflows/ci.yml | `grep -n '"test"' package.json` → 8:"test": "vitest run"
这个仓库的规矩  | AGENTS.md / eslint.config.js  | `sed -n '1,40p' AGENTS.md`
```

规则：**没有路径或命令输出的行不许写。** 「看起来像 MVC」不是证据；`grep` 出来的一行才是。
看不清的就写「未见证据」，不要填一个合理答案。

## 第 3 步——回答"这次改动该落在哪"，给三个候选接缝

对每个候选写：**在哪（路径/函数）**、**为什么是这里（引用一条代码事实）**、**代价（要改几处、会不会破公共接口）**、
**怎么证明改对了（一条能变红的命令）**。

排序原则：

- 优先**已有接缝**（已存在的抽象、依赖注入点、中间件、hook），而不是新造一个；
- 优先**改动小且可演示**的路径（一次能跑通），而不是"先把架构重构成理想状态"；
- 如果三条都代价很高，**先说这件事不该在这做**，并给出更合适的层次。

## 第 4 步——把"改动前基线"先跑一遍

```bash
<仓库自己的测试命令>     # 现在就必须知道它是绿的还是本来就有红
```

**动手之前先记录基线**。否则改完之后你无法区分"我弄坏了"和"本来就坏"。红着的套件不是停手的理由，
是**只能拿"不比基线更差"当判据**的理由——把失败清单存下来。

## 第 5 步——交付地图，等确认

一次交付四样：**地图表**、**三个候选接缝（含代价与判据）**、**基线命令与结果**、**你看不到的部分**
（读不到的文件、跑不起来的环境、需要凭证的东西）。

**在用户确认之前不改代码。** 这一步不是礼貌，是因为地图错了之后的所有改动都要返工。

## 拒绝清单（硬契约）

- 不读工作区之外的文件，也不假装读过；
- 不猜测试/构建命令——只从配置文件与 CI 里读；
- 不写没有路径或命令支撑的结论；
- 不在没跑基线的情况下说"改好了"；
- 不为了显得彻底而通读整个仓库（上下文会先耗尽，地图反而不准）；
- 不在勘察阶段顺手改代码，即使看到明显的小毛病——记下来，交付时点名。

## 与其它技能的接线

- 决定了**要改什么、按什么顺序改** → `to-tickets`（切成可单独演示的工单）或 `to-spec`（写成规格）；
- 开始改 → `tdd`（先写会变红的测试）、`implement`（按规格/工单实现）；
- 改完 → `code-review`（两条轴评审）与 `evidence-first-delivery`（交付前自证）；
- 遇到看不清的缺陷 → `diagnosing-bugs`；要重新设计接口 → `codebase-design`。
