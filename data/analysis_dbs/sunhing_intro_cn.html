Management Briefing

从模拟经营数据到可执行的管理分析驾驶舱

本页用于从管理层视角解释 Sun Hing 研究在 LangConfig 中的整体构造。数据库负责保存经营事实， SKILL.md 负责沉淀业务解释框架，dashboard HTML 负责形成统一展示入口，而分析对话负责把业务语义与 SQL 校验结合起来，输出可执行结论。

当前体系在 dashboard 选择与上下文绑定层已经实现 metadata-driven；但在页面布局和内容编排层，仍主要由 Python 脚本驱动，尚未完全过渡为由 SKILL.md 主导生成。

2. 端到端流程

下面这版是基于当前代码实现与 agent 行为梳理出的正式业务流程。
1

数据清洗与输入

Sun Hing 当前案例使用模拟经营数据，经过整理后装载进结构化 SQLite 分析数据库，作为后续所有展示与问答的底座。

  • raw source tables 保留业务明细
  • dimension + fact tables 支撑 KPI 与 ROE 分析
  • ERD 负责把 schema 与 lineage 解释清楚
2

伴随技能文件

SKILL.md 是数据库的语义伴随层。它不保存事实本身，而是定义事实应如何被理解、归类与解释。

  • 业务背景
  • KPI / 因子分组
  • 优先查询路径
  • 何时使用 fact 表，何时回退 raw 表
3

HTML 生成

当前 Sun Hing dashboard 主要由 Python 直接读取 SQLite 后生成，并在 HTML 头部嵌入 skill metadata，完成上下文绑定。

  • 当前状态：Python-first 布局生成
  • HTML metadata 负责连接 DB + skill + entry mode
  • 目标状态：更强的 SKILL.md-driven generation
4

主页面与详情页

整个 study 由一个主 Hub 页面与多个 detail pages 组成，用于按管理问题逐层下钻。

  • 主 hub = executive cockpit
  • detail pages = 因子仪表盘
  • ERD / Gantt = 解释性页面
5

LangConfig UI

Analysis UI 以当前选中的 dashboard HTML 作为整个分析上下文锚点，统一组织后续所有模块。

  • 在 iframe 里展示 hub HTML
  • 给 Data panel 加载 embedded data
  • 给 Skill panel 加载关联技能文件
  • 依据 dashboard metadata 配置 chat 上下文
6

分析对话

Chat 虽然由 skill 引导，但实际回答仍依赖后端系统提示、SQL 工具与必要的 Python 工具共同完成。

  • 读取 dashboard 绑定的 skill metadata
  • 装载 SKILL.md 内容
  • 对 SQLite 执行 SQL 做验证
  • 最终用业务语言回答，而不是只复述 schema

4. 各类 Artifact 的职责边界

最容易产生误解的地方，通常是把 source-of-truth、semantic layer 与 presentation layer 混在一起。

Database / Schema

SQLite DB 是事实底座，存放真实记录以及用于分析的 KPI / ROE 汇总 fact tables。

含义：数据真相层。

ERD HTML

ERD 页面是解释层，用来说明 raw tables、dimension tables 和 fact tables 之间的关系与数据流向。

含义：schema 说明层。

SKILL.md

技能文件是业务语义伴随层，它把表结构翻译成管理语言，例如 ROE 因子、KPI 家族和推荐查询顺序。

含义：业务解释层。

Dashboard HTML

仪表盘是用户首先接触到的展示页，但它不是数值真相的最终权威。

含义：可视化与导航层。

Analysis UI

LangConfig 的 Analysis 页面以当前选中的 HTML 为锚点，把 dashboard、skill panel、data panel 和 chat panel 统一组织起来。

含义：用户操作界面。

Analysis Chat

Agent 读取 dashboard 关联 skill，执行 SQL 查询 SQLite，并用业务语言给出回答；它应先校验数值，而不是直接照抄 HTML。

含义：由 skill 引导的 SQL 推理层。

5. LangConfig 中的用户旅程

下面这部分描述的是：一个用户从进入 study 到提出管理问题，整个体验如何发生。

A. 打开主 Hub

用户先打开 Sun Hing 主仪表盘，该页面相当于整个 study 的统一入口与总览页。

为什么重要：用 hub HTML 做入口，比直接暴露所有 detail pages 更容易治理。

B. 浏览详情页

用户可以从 Hub 继续进入 Profit、Turnover、Leverage、Support、Risk、ERD 与 Gantt 页面。

为什么重要：每个页面都在缩小管理视角，但不会切换 study 上下文。

C. 查看 Data 与 Skill

UI 可以基于当前 HTML 读取 embedded dashboard data，并同步加载与之绑定的 skill 内容。

为什么重要：用户看到的不只是图形结果，还能看到源数据和业务解释。

D. 发起分析提问

用户在 Analysis Chat 中输入自然语言问题，例如询问某个 ROE 因子、某项 KPI 或管理异常点。

为什么重要：问题会带着业务 study 的语义上下文被解释，而不是变成通用 SQL 问题。

E. Agent 解析上下文

后端读取 dashboard metadata，装载 skill，解析 DB path，并携带 SQL 工具启动 deep agent。

为什么重要：当前选中的 HTML 会自动决定正确的 study context。

F. SQL 校验并回答

Agent 对 SQLite 执行 SQL，用 SKILL.md 解释结果，最后返回管理层可直接阅读的业务回答。

为什么重要：答案来源是数据库真相，而不是页面卡片上的静态显示值。

6. 当前状态 vs 目标状态

这张表概括了当前体系的关键架构定位，以及后续可持续演进方向。
主题 当前状态 目标方向
数据真相 SQLite DB 是 source of truth。 继续坚持 DB-first，不能把 truth 转移到静态 HTML。
业务语义 SKILL.md 承担业务解释层角色。 继续强化 semantic contract，而不是把 SQL 写死。
Dashboard 生成 目前仍以 Python 驱动布局与计算逻辑。 逐步走向更强的 SKILL.md-driven dashboard structure。
Dashboard 选择 已经通过 HTML meta block 实现 metadata-driven。 这个模式应继续复用于未来更多 business study。
Analysis Chat 由 skill + backend prompt + SQL/Python tools 共同驱动。 保持直接回答风格，同时继续坚持 SQL 验证。
关键设计原则：DB 保存事实，SKILL.md 保存业务含义，HTML 负责展示与导航，Analysis Chat 将三者整合，形成可落地的企业研究分析体验。

7. 建议阅读路径

如果一个新用户希望快速建立整体认知，建议按以下路径进入。

路径 1：管理视角

先看主仪表盘，再按管理问题下钻到具体 factor pages。

路径 2：数据理解

先读 ERD，理解 raw tables、dimension、fact tables 与 lineage，再去核对指标。

路径 3：业务语义

阅读关联的 SKILL.md，理解每个因子的管理含义，以及 agent 应如何解释自然语言问题。

路径 4：Agent 验证

通过 Analysis Chat 提问，在核对 dashboard 数字时坚持走 SQL 验证。
